# IBCI 技术文档书写准则

> 本文档是 IBCI 全部技术文档的强制书写准则。对象为输入/修改 `docs/` 目录下技术文档的写作者。
> 按写作者的决策流程组织：先定归属，再搭骨架，再写段落，再套格式，最后验收。
> 任何新增或修改技术文档内容时，对照本文件自查。
>
> **适用范围**：`docs/syntax/`、`docs/architecture/`、`docs/subsystems/`、`docs/KNOWN_LIMITS.md` 及
> 各索引手册（`SYNTAX_REFERENCE.md`、`ARCHITECTURE.md`、`SUBSYSTEM_DESIGN.md`）。`tasks_docs/` 和
> `tests_docs/` 不在本准则管辖范围内。

---

## A. 体系设计：写之前先定归属

### A.1 文档的唯一目的

技术文档的唯一目的：**让读者在不依赖作者的情况下，独立建立对系统的心智模型，并能基于该模型做出正确决策。** 文档不是工作日志、代码的散文翻译、决策过程的会议记录。

### A.2 动笔前三问

读者是谁？读完后要能做什么？当前不知道什么（文档只填补这个缺口）？

### A.3 文档四分法（Divio 体系）

IBCI 文档体系遵循 Divio 文档四分法，每篇文档应明确自身属于以下哪一类，并使用对应的写作风格：

| 类型 | IBCI 对应 | 写作要求 |
|------|-----------|----------|
| **教程（Tutorial）** | `docs/guide/` | 面向初学者，按步骤引导，每步结果可预期，允许省略细节 |
| **操作指南（How-to）** | 当前缺失 | 面向有基础的用户，解决具体问题，以问题为标题，列出步骤 |
| **参考（Reference）** | `docs/syntax/` | 信息完备，描述精确，每个章节独立可读，不解释为什么 |
| **解释（Explanation）** | `docs/architecture/`、`docs/subsystems/` | 面向理解，阐述设计理由与背景，提供概念框架 |

同一篇文档不得同时充当两种角色。例如，在语法参考中穿插设计理由叙述会干扰读者定位。

### A.4 概念归属唯一

每个概念有且仅有一个文档拥有其完整解释。其他文档引用它，不复制它。部分复制必然漂移——两处描述同一事物，改一处忘另一处，读者不知哪处为真。

### A.5 体系是设计出来的

新增文档前必须回答：这个概念的归属文档是谁？归属文档已存在则扩展它；必须新建则明确它在体系中的位置。应显式设计文档体系的结构（哪些文件存在、各自覆盖什么、如何组合为整体）。

### A.6 文件身份完整性

标题、定位段、实际内容三者必须一致。文件名承诺什么，内容就必须交付什么。新增内容若不匹配文件已声明的范围，放入正确的归属文件，而非追加到当前文件。

### A.7 层间正交

语法手册回答"怎么写"，架构文档回答"为什么这样"，子系统文档回答"内部怎么实现"。同一事实不在两层重复描述。抽象粒度递进：

| 层级 | 允许出现 | 不允许出现 |
|------|---------|-----------|
| `syntax/` | 语法形式、类型签名、用户可见行为 | 编译器内部类名（如 `IbBehaviorExpr`）、实现模块路径 |
| `architecture/` | 架构概念、设计理由、组件关系、内部类名 | 逐行代码解释 |
| `subsystems/` | 实现细节、模块交互、数据流、代码路径 | 语法使用说明（属于 syntax/） |

### A.8 信息架构：读者旅程

文档按读者旅程组织，而非按代码文件组织。一个读者解决一个典型问题需要跨越哪些文档？这些文档之间如何引导？

每个文档的定位段应明确读者需要的前置知识，并在末尾的"深入指引"中给出下一步阅读方向。跨文档的引用链形成多个"读者旅程线"——例如：

> 新用户旅程：根 README → GETTING_STARTED（导航页）→ docs/guide/ → SYNTAX_REFERENCE（查语法）→ KNOWN_LIMITS（查边界）
> 编译器开发者旅程：ARCHITECTURE（01-03）→ 子系统（intent_system）→ 源码

## B. 文档结构：骨架

### B.1 单篇文档骨架

```
标题（精确描述覆盖范围的名词短语）
├── 定位段（1-3句：本文是什么、给谁看、覆盖什么）
├── 核心概念（读者必须建立的心智模型）
├── 主体内容（按读者认知顺序，非按代码文件顺序）
├── 约束与限制（读者必须知道的边界）
└── 深入指引（可选：指向更细节的文档，非必须阅读）
```

**示例——合格的定位段**：

> 本文档描述 IBCI 虚拟机的正式执行规范，包括 CPS 调度循环、内存模型、LLM 数据流与并发模型。
> 面向需要实现或验证 IBCI 运行时的开发者。阅读前需了解 AST 节点类型（见 architecture/02_metadata_ast.md）。

**示例——不合格的定位段**：

> 本文档是关于 VM 的。（❌ 未说明覆盖范围、读者对象、前置知识）

### B.2 渐进披露（倒金字塔）

最重要的信息在最前面。读者可能只读第一段就离开——第一段必须传达核心。读者可能只读标题就停止——每个标题本身必须是信息性的。如果一个读者只有 30 秒，他至少应能获取本文的核心不变量。

**示例——信息性标题**：

> ### 2.3 意图优先级（消解顺序，在 LLM 调用内）（✓ 标题即答案）
> ### 2.3 关于意图的一些说明（✗ 标题不包含信息）

### B.3 章节是论证链的环节

每章回答一个明确的问题，章节间存在逻辑推进关系（递进 / 并列 / 总分 / 对比）。章节标题是名词短语（回答"什么"），不是动词短语（"实现X"）。不按代码文件顺序排列。

**示例——合格与不合格的章节标题**：

> ### 三、意图优先级与消解顺序（✓ 名词短语，回答"什么"）
> ### 三、实现意图消解（✗ 动词短语，回答"怎么做"）

### B.4 信息密度有节奏

章节开头低密度（建立方向）→ 核心论述高密度（规则、表格）→ 示例中密度（呼吸空间）→ 边界中低密度。全文高密度无喘息是反模式；全文低密度（水）也是。

## C. 段落与行文：肌肉

### C.1 段落是最小论证单元

段落不是"几句话的集合"。三要素：

1. **主题句**（第一句）：声明本段要建立的一个事实。仅读此句即可获取核心信息。
2. **支撑**（中间）：解释机制、给出约束、提供示例。不引入新论点。
3. **收束**（可选末句）：点明边界、例外、或引出下一段的问题。

**检验**：遮住中间和末尾，仅读第一句——若无法判断"这段在讲什么"，主题句不合格。

**示例——合格段落**：

> 意图上下文随执行帧持有，而非全局单例。每个执行帧（`IExecutionFrame`）在创建时从调用者帧 fork 一个意图上下文副本，帧内对意图上下文的任何修改（`@+`、`@-`、`@!`）仅对该副本生效。函数返回时副本被丢弃，调用者的意图上下文不受影响。这种帧级隔离保证了意图操作不会跨函数泄漏。

**示例——不合格段落**：

> 意图上下文是一个很重要的概念。我们之前讨论过它的实现方式。目前它是随帧持有的，这意味着每个帧都有自己的副本。之前我们考虑过全局单例的方案，但后来发现有问题，所以改成了帧级隔离。（❌ 主题句不明确，含历史叙述，未收束）

### C.2 行文四规则

| 规则 | 说明 |
|------|------|
| 陈述式，非探索式 | 陈述已确定的事实，不记录探索过程 |
| 现在时态，非历史时态 | 描述当前状态，不描述演变。变更历史属于 git |
| 主动语态，明确主语 | "编译器发出错误"而非"错误会被发出" |
| 精确且完备 | 精确 = 读者能据此判断自己的代码是否合规；完备 = 不存在需要猜测的隐含条件 |

### C.3 术语管理

首次出现时**用粗体标注**一句话定义，后续不重复。一词一义，一义一词。代码标识符（`IbFileHandle`）与散文术语（"文件容器"）对应但不混用。

### C.4 设计理由的书写

遵循"约束 → 决策 → 后果"三段式：因为 [不可改变的外部条件]，系统选择 [具体方案]，这意味着 [读者需要知道的行为影响]。

不写探索过程（"试了A不行又试了B"），不写无约束的决策（"使用协议驱动"——为什么？），不写无后果的约束（"因为性能"——所以对我有什么影响？）。

**示例**：

> 因为 LLM 调用的 HTTP 往返延迟远大于本地计算，系统选择将行为表达式的结果类型绑定到左值声明类型上，而非运行时动态推断。这意味着编译器可以在编译期确定输出格式约束，避免每次 LLM 调用增加一次额外的类型推断往返。

### C.5 表格 vs 散文

多个对象具有相同属性维度（平行对比）→ 表格。单个概念的因果链解释 → 散文。信息是枚举性的 → 表格。信息是推导性的 → 散文。表格列数不超过 5。

### C.6 示例设计

- **最小充分**：只含说明当前论点所需的最少元素
- **配对出现**：正面 + 反面
- **注释说明意图**（"为什么选择这种写法"），不解释代码做了什么
- **排列顺序**：规则反直觉时先示例后规则（归纳）；规则自然时先规则后示例（演绎）

**示例——正面与反面配对**：

```ibci
# ✅ 正确：通过有类型的局部变量明确输出约束
func get_reply() -> str:
    str reply = @~ 给我一句话 ~
    return reply
```

```ibci
# ❌ 错误：行为表达式不可直接用于 return——编译器无法推导输出类型约束
func get_reply() -> str:
    return @~ 给我一句话 ~
```

### C.7 可读性约束

| 维度 | 约束 |
|------|------|
| 句子 | 单句不超过 40 字（中文）。超过则拆分 |
| 段落 | 不超过 8 句。超过则检查是否混入第二个论点 |
| 嵌套 | 列表嵌套不超过 3 层。超过则拆为独立小节 |
| 代码块 | 文档中代码片段不超过 20 行。超过则考虑引用源文件 |
| 表格 | 列数不超过 5。超过则拆分或改用散文 |
| 单篇长度 | 超过 500 行时审视是否应拆分 |

## D. 条目格式模板：骨骼

技术手册中大量出现"平行小节"——每个小节对一个特定的 API、类型、协议、模块作说明。这些平行小节必须遵循**严格一致的格式模板**，使读者建立阅读预期后能快速定位信息。

### D.1 五种模板

**函数/API**：签名 → 一句话说明 → 参数表 → 返回语义 → 约束/前置条件（如有）→ 错误/诊断码（如有）→ 示例（正面+反面）。

**数据类型**：一句话定位 → 继承/组合关系 → 字段表 → 核心不变量（2-5条）→ 与其他机制的交互（如有）→ 示例。

**协议方法**：一句话职责 → 签名 → 调用时机 → 契约（实现者保证什么 / 调用者依赖什么）→ 默认行为（如有）→ 示例。

**技术模块**：一句话定位 → 职责边界（做什么/不做什么）→ 对外接口表 → 内部结构（如需）→ 与其他模块的关系 → 约束。

**诊断码**：一句话说明 → 精确触发条件 → 严重级别 → 修复方式 → 示例（触发代码 + 修正代码）。

### D.2 一致性原则

同一文档内所有平行小节必须使用同一模板。槽位要么填写要么整行省略，不得留空或写"无"。一句话说明必须是完整陈述句。表格列数在同一文档内保持一致。

### D.3 模板骨架速查

```
函数/API                          数据类型
─────────────────────────────     ─────────────────────────────
### `名称`                        ### 名称
签名（参数 → 返回）                一句话定位（是什么、在体系中的角色）
一句话说明。                       继承/组合关系
**参数**：| 参数 | 类型 | 说明 |   **字段**：| 字段 | 类型 | 语义 |
**返回**：语义说明。               **核心不变量**：（2-5条）
**约束**：（如有）                 **与其他机制的交互**：（如有）
**错误**：诊断码 + 触发条件        **示例**：构造 + 基本使用
**示例**：正面 + 反面

协议方法                          技术模块
─────────────────────────────     ─────────────────────────────
### `__方法名__`                  ### 模块名
一句话职责。                       一句话定位（解决什么问题）
**签名**：输入 → 输出             **职责边界**：做什么 / 不做什么
**调用时机**：谁在何时调用         **对外接口**：| 接口 | 说明 |
**契约**：实现者保证 / 调用者依赖  **内部结构**：（如需）
**默认行为**：（如有）             **与其他模块的关系**
**示例**：一个具体实现片段         **约束/限制**

诊断码
─────────────────────────────
### `DIAGNOSTIC_CODE`
一句话说明（何时产生）。
**触发条件**：精确规则（无歧义判断）。
**严重级别**：ERROR / WARNING。
**修复方式**：如何消除。
**示例**：触发代码 + 修正代码。
```

### D.4 模板应用示例

以下展示一个诊断码条目从模板到实际内容的完整过程：

**模板**：

```
### `DIAGNOSTIC_CODE`
一句话说明（何时产生）。
**触发条件**：精确规则。
**严重级别**：ERROR / WARNING。
**修复方式**：如何消除。
**示例**：触发代码 + 修正代码。
```

**实际填写**：

```
### `SEM_INTENT_PLACEMENT`
意图注释放置位置不合法。
**触发条件**：连续两个 `@` 或 `@!`（one-shot 意图）之间无可执行语句，或 `@`/`@!` 后无下一条可执行语句。
**严重级别**：ERROR。
**修复方式**：在 `@`/`@!` 后紧跟一条可执行语句，或移除多余的意图注释。
**示例**：
触发代码：
@ 意图A
@ 意图B           # ← 连续两个 one-shot，不允许
str r = @~ MOCK ~
修正代码：
@ 意图A
str r = @~ MOCK ~ # ← 紧跟一条可执行语句，合法
```

## E. 红线：禁止书写的内容

| 禁止 | 原因 |
|------|------|
| 过程叙述（"经过讨论/验证/实测..."） | 读者只需结论 |
| 历史演变（"旧X已删除，现为Y"） | 属于 git 历史 |
| 日期戳 / 完成标记（"已解决"、"已落地"、"最后更新：..."） | 文档正确则不需时间证明；不正确则时间不能拯救 |
| 未实现的设计（除非独立"规划"章节且明确标注） | 文档描述当前真实行为 |
| 任务编号 / 里程碑代号 / PR 编号 | 对读者是噪音 |
| 代码的散文翻译（逐行解释代码做了什么） | 代码自己会说 |
| 核查记录 / 验证清单 / 进度表 / 状态追踪 | 过程产物，属于 git 或 `tasks_docs/` |
| 只有作者能理解的缩写/代号 | 用描述性名称替代 |
| 混合抽象层级（用户语法和编译器内部类名同段出现） | 读者无法确定自己在哪个层级思考 |
| 过时信息 | 比没有信息更危险 |
| 未标注的假设 | 读者无法判断自己是否具备理解条件 |

## F. 引用与代码片段：工具

### F.1 引用

引用是补充，不是替代。删掉引用后当前段落必须仍然可理解。若删掉后信息量归零，说明当前文档缺少自己的叙述——修复方式是补全叙述，而非保留引用。

引用的正确用途："本机制的完整形式化定义见 X"（当前已给出足够理解的摘要）。不用行号（用模块路径+类/函数名、章节名、或概念名）。不引用已删除/重组的路径。FAQ 必须附着于其所澄清的文档。

### F.2 代码片段

代码片段三条件（必须同时满足）：
- 有上下文说明（在做什么、为什么出现）
- 自包含（不需打开源文件即可理解）
- 必要（自然语言无法同等精确表达）

做不到则删除，改用自然语言。

### F.3 代码注释与文档的边界

对"正在修改这行代码的人"有用的信息是注释（局部设计意图、已知陷阱、不变量声明）。对"使用这个系统的人"或"理解这个设计的人"有用的信息是文档（完整机制、概念模型、使用指南）。

## G. 质量检验：验收

### G.1 段落级

遮住段落中间和末尾，仅读第一句——能否判断"这段在讲什么"？

### G.2 文档级（5 分钟测试）

一个具备基本背景知识的新读者，花 5 分钟阅读本文后，能否：
1. 说出本文覆盖什么、不覆盖什么
2. 说出核心不变量（1-3 条）
3. 知道在哪里找到更细节的信息
4. 不会基于本文做出错误的使用决策

任何一条不满足则文档不合格。

### G.3 体系级

本文描述的概念，其归属文档是否是本文？是否存在另一处部分复制了同一内容？删掉所有引用后本文是否仍然自包含？

### G.4 文档健康检查清单

新增或重大修改文档后，逐项通过：

- [ ] 有定位段（1-3句：本文是什么、给谁看、覆盖什么）
- [ ] 标题是名词短语，精确描述覆盖范围
- [ ] 定位段、标题、实际内容三者一致（§A.6）
- [ ] 无日期戳、无"最后更新"、无"已解决"标记
- [ ] 无历史叙述（"原实现采用..."、"经过讨论..."）
- [ ] 无任务编号（PT-xxx）、里程碑代号、PR 编号

## H. 文档评审流程

新增或重大修改的文档需经过以下评审：

1. **自检**：走完 §G.4 健康检查清单，逐项勾选
2. **同行评审**：一个非作者读者花 5 分钟阅读后，能否正确回答 §G.2 的四个问题
3. **一致性检查**：确认新增/修改内容不与已有文档的描述冲突（§A.4 概念归属唯一）
4. **链接检查**：确认所有跨文档引用路径有效，不存在指向已删除文件的链接
