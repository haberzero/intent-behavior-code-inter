# 如何使用仓库测试套件的自身安全机制（卡死识别 / 超时配置）

> 面向需要运行本仓库测试套件、或在测试中引入并发/等待逻辑的开发者。
> 解决"测试卡死时如何被自动识别与定位、超时如何配置"的具体问题。
> 前置知识：`docs/guide/00_environment.md`（测试环境搭建）、
> Python 基础（threading 概念即可，无需深入）。
> 机制归属：超时配置单点在 `pytest.ini`，进程级看门狗在 `tests/conftest.py`
> （头部注释含双层防护说明）——本文只讲怎么用，机制细节以这两个文件为准。

## 机制总览（30 秒）

测试套件有**两层自动卡死防护**，卡死时套件自己报告"谁卡死、卡在哪行"，
无需外部手动超时或输出捕获：

| 层 | 触发场景 | 报告形态 |
|---|---|---|
| 第一层（每测试超时，`pytest-timeout` 插件） | 单个测试卡死（线程 join 无界等待、等待子进程/子线程、死锁） | 该测试**自动 FAIL**，报告含**测试名 + 全部线程栈**（精确到卡死行） |
| 第二层（进程级看门狗，`tests/conftest.py`，**阶段感知**） | pytest 框架层卡死（collect/插件死锁——测试级超时不生效的场景）。**职责止于框架层**：测试执行完毕（sessionfinish）即解除——teardown（unconfigure 期 GC）慢 ≠ 死锁，不与套件总时长竞态 | 进程以退出码 **124** 终止，全部线程栈（`dump_traceback` 输出）写入 `.tmp_pytest/deadlock_watchdog_dump.txt` |

## 运行测试（常规用法）

```bash
python -m pytest tests/            # 全量（唯一权威命令；结果计数以实跑为准）
python -m pytest tests/compiler    # 按目录跑子集
python -m pytest tests/runtime/test_environment_type.py   # 单文件
```

- 全量耗时为分钟级（含解释器启动与并发/IO 用例）——**分钟级等待属正常**，
  不等于卡死。
- 卡死的判定信号：某个**单个测试**长时间无进展且最终报 `Timeout`（第一层
  触发），或整个 pytest 进程无输出退出 124（第二层触发）。

## 卡死发生时：读第一层报告

单个测试卡死时，`pytest-timeout` 自动终止该测试并输出如下形态的报告
（示例）：

```
+++++++++++++++++++++++++++++++++++ Timeout ++++++++++++++++++++++++++++++++++++
tests/xxx/test_yyy.py::test_some_name
  ...
  File ".../test_yyy.py", line 12, in test_some_name
      worker.join()
+++++++++++++++++++++++++++++++++++ Timeout ++++++++++++++++++++++++++++++++++++
1 failed in 60.12s
```

**读法**：

1. `Timeout` 分节标题下的**测试路径::名称** = 卡死的测试项（直接定位到
   具体测试，无需逐文件排查）。
2. 该测试的**调用栈**（分节内）= 卡死时该线程停在的一行（如
   `worker.join()`——无界 join 是典型卡死源）。
3. 其余线程栈（如输出）= 判断是"等它"还是"它等别人"（死锁环识别）。

报告后套件**继续运行其余测试**（仅该测试 FAIL），不中断整轮。

## 出现"无输出退出 124"时：读第二层

整个 pytest 进程无正常结果输出、以退出码 124 结束 = 进程级看门狗触发
（框架层卡死——collect/插件死锁；看门狗阶段感知，测试执行完毕后即解除，
故触发即意味着框架层真卡死，非时长竞态）。**读取全部线程栈 dump 文件
`.tmp_pytest/deadlock_watchdog_dump.txt`**（阶段无关通道：collect 期卡死的
stderr dump 会被 pytest 的 fd capture 吞没，文件通道任何阶段触发皆可读；
不要用 `tail` 截断——线程栈输出较长）：

1. 找到 `Current thread` 与各线程栈段（`faulthandler` 格式）。
2. 卡死线程 = 停在 `join`/`wait`/`acquire`/`get`（队列）等阻塞调用上的
   线程；多个线程互等 = 死锁环。
3. 若线程栈显示 pytest 正在 collect 某文件/导入某模块——卡死在框架层
   （插件、conftest 导入链），检查最近改动。

## 超时配置（调整）

- **全局每测试上限**：`pytest.ini` 的 `timeout`（当前 60 秒）。调大/调小
  改这一行即可，全部测试生效。
- **单测试覆盖**：

  ```python
  import pytest

  @pytest.mark.timeout(300)      # 该测试单独放宽到 300s（长用例）
  def test_slow_io(): ...

  @pytest.mark.timeout(5)        # 该测试收紧（快速失败面）
  def test_quick_check(): ...
  ```

- **单次运行临时覆盖**（不改文件）：

  ```bash
  python -m pytest tests/ --timeout=120
  ```

- **禁用超时**（调试卡死现场时用）：`python -m pytest tests/ -p no:timeout`
  ——卡死会持续挂起，需手动终止；第二层看门狗仍兜底。

## 编写新测试时的卡死防范

在测试中引入线程/等待/子进程逻辑时，让等待**有界**：

- 线程 join 传超时：`t.join(timeout=10)`，超时后断言/清理，不用无界
  `t.join()`。
- 等待带状态的句柄/队列时给等待设上限，并以**有限超时**断言"应完成"。
- 本仓库隔离执行（`ihost.spawn_isolated` / `collect`）的 `collect`
  默认无界等待——测试中经隔离策略传有限超时（见
  `docs/howto/use_isolation.md` 的超时面），勿让测试依赖"子任务必然
  及时完成"的假设。

长耗时但有明确上界的用例（如真实网络重试测试），用
`@pytest.mark.timeout(...)` 显式声明其上界，而不是调大全局值。

## 边界与注意

- 第一层超时按**单个测试**计——全量套件的总时长可以远大于 60s，这是
  正常的，不构成卡死信号。
- 第一层报告定位的是"卡死测试停在哪行"，不直接给出根因（根因需结合
  线程栈判断等待关系）；死锁环通常表现为两个以上线程互相等待。
- 第二层退出码 124 与系统 `timeout` 命令的退出码相同——若你在外部又套了
  `timeout 120 pytest ...`，无法区分是哪层触发；本仓库约定**不**在外部
  加 `timeout`，由套件自身两层防护兜底。
- 超时值针对本机开发环境校准；CI 慢机若出现误报（正常测试越过 60s），
  优先用 `@pytest.mark.timeout(...)` 给该用例单独放宽，并评估是否反映
  了该用例的合理上界。
