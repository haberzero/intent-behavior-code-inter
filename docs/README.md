## 三、文档治理纪律（强制）

### 3.1 单点真理

| 事实 | 唯一来源 |
|------|---------|
| 当前最紧要任务 | `tasks_docs/NEXT_STEPS.md` |
| 阻塞/搁置事项 | `tasks_docs/PENDING_TASKS.md` |
| 语言级限制 | `docs/KNOWN_LIMITS.md` |
| 语法权威 | `docs/SYNTAX_REFERENCE.md` + `docs/syntax/` |
| 架构设计 | `docs/ARCHITECTURE.md` + `docs/architecture/` |
| 子系统设计 | `docs/SUBSYSTEM_DESIGN.md` + `docs/subsystems/` |

### 3.2 数字纪律（测试基线）

- 测试基线**只在 `tasks_docs/NEXT_STEPS.md` 顶部**写一次。
- 其它文档**不得冻结具体测试通过数字**，统一用"以 `python -m pytest tests/` 实跑为准"。

### 3.3 生命周期纪律

- 重大架构决策直接写入 `docs/architecture/` 对应章节，不再使用独立 ADR 文件。
- 已实现且无延迟项的设计内容可从任务文档中删除。
- 每次开新分支前，先复跑测试基线。

### 3.4 跨文件一致性

`README.md`、`KNOWN_LIMITS.md`、`SYNTAX_REFERENCE.md`、`ARCHITECTURE.md` 之间对同一语法/限制/架构立场的描述必须用**同一组事实**。

### 3.5 新增文档前的检查

- 新增 AST 字段或侧表前，必须先在 `architecture/02_metadata_ast.md` 查证。
- 新增长期文档前，先确认它不与现有文档重复--若重复，扩展现有文档而非新建。

### 3.6 代码注释卫生纪律

> **核心原则**：代码注释只应注明**功能设计**与**已知问题**，不应承载项目过程信息（任务指针、设计代号、历史叙述、文档章节引用）。过程信息属于任务文档与 git 历史，不属于代码。

**禁止在 `.py` 文件的注释与 docstring 中出现的内容**：

| 类别 | 违规示例 | 处置 |
|------|---------|------|
| 任务文档指针 | `见 NEXT_STEPS.md`/`PENDING_TASKS §四`/`tasks_docs/` | 删指针，留功能说明 |
| ADR 编号 | `Per ADR-019：`/`（ADR-020 §A）` | 删编号前缀/后缀，留设计解释 |
| PT 任务编号 | `PT-ARCH-28：`/`PT-4.7：` | 删编号前缀，留功能说明 |
| 设计代号 | `G1-G6`/`D1-D6`/`H1-H3`/`NS-x`/`P0-P7`/`方案A-B`/`C2-C11` | 删代号标签，留功能说明 |
| 历史叙述 | `原实现采用…`/`历史上…`/`旧 bug`/`修复见PR`/`合并自`/`Source:`/`legacy` | 改写为现在时或删除 |
| 文档章节号 | `§6.1`/`§9.2`/`§三` | 删章节号，留功能说明 |
| 文档路径指针 | `docs/architecture/…`/`docs/KNOWN_LIMITS.md` | 删指针行/分句 |

**保留的内容**（不视为违规）：

| 类别 | 说明 |
|------|------|
| 诊断码 | `SEM_TYPE_MISMATCH`/`PAR_EXPECTED_TOKEN`/`LEX_INVALID_CHAR` 等命名制诊断码（定义见 `core/base/diagnostics/codes.py`），是功能性错误码 |
| 公理码 | `SC-3`/`LT-2`/`EXEC-2`/`ISO-4`/`OM-2`/`GC-2`/`LLM-1`/`IC-1` 等 VM 规范公理编号（定义见 `docs/architecture/05_vm_specification.md §8`），是规范契约码 |
| 功能性术语 | "锚点"（path anchor）、"Layer N / Phase N / STAGE N"（算法阶段）是功能描述 |
| 诊断码常量赋值 | `SEM_TYPE_MISMATCH = "SEM_TYPE_MISMATCH"` 是代码，不是注释 |

**新增代码时的自查**：提交前对自己的改动运行以下检查，确保未引入违规：

```bash
# 搜索违规模式（ADR/PT/任务文档指针/章节号）
grep -rnE 'ADR-[0-9]|PT-ARCH|PT-[0-9]|Per ADR|§[0-9]|tasks_docs/|PENDING_TASKS|NEXT_STEPS' --include='*.py' <changed-files>
# 搜索设计代号
grep -rnE '\b(G[1-6]|D[1-6]|H[1-3]|NS-[0-9]|P[0-7]-[0-9A-Z])\b' --include='*.py' <changed-files>
# 搜索历史叙述
grep -rnE 'legacy|历史|旧 bug|修复见PR|合并自|Source:' --include='*.py' <changed-files>
```

命中后逐条判断：是注释/docstring 则清洁（删标记留功能），是诊断码/公理码或功能性术语则保留。

**诊断码使用规则**：生产代码中不得使用字符串字面量（如 `code="SEM_TYPE_MISMATCH"`）引用诊断码，必须从 `core/base/diagnostics/codes.py` 导入常量引用（如 `code=SEM_TYPE_MISMATCH`）。新增诊断码时在 `codes.py` 中定义新常量即可，无需分配编号。

## 六、技术文档书写准则（强制）

> 本节是 IBCI 全部技术文档的书写准则。按写作者的决策流程组织：先定归属，再搭骨架，再写段落，再套格式，最后验收。
> 任何新增或修改文档内容时，对照本节自查。

---

### A. 体系设计：写之前先定归属

技术文档的唯一目的：**让读者在不依赖作者的情况下，独立建立对系统的心智模型，并能基于该模型做出正确决策。** 文档不是工作日志、代码的散文翻译、决策过程的会议记录。

**动笔前三问**：读者是谁？读完后要能做什么？当前不知道什么（文档只填补这个缺口）？

**概念归属唯一**。每个概念有且仅有一个文档拥有其完整解释。其他文档引用它，不复制它。部分复制必然漂移——两处描述同一事物，改一处忘另一处，读者不知哪处为真。

**体系是设计出来的，不是长出来的**。新增文档前必须回答：这个概念的归属文档是谁？归属文档已存在则扩展它；必须新建则明确它在体系中的位置。文档体系的结构（哪些文件存在、各自覆盖什么、如何组合为整体）应被显式设计。

**文件身份完整性**。标题、定位段、实际内容三者必须一致。文件名承诺什么，内容就必须交付什么。新增内容若不匹配文件已声明的范围，放入正确的归属文件，而非追加到当前文件。

**层间正交**。语法手册回答"怎么写"，架构文档回答"为什么这样"，子系统文档回答"内部怎么实现"。同一事实不在两层重复描述。抽象粒度递进：syntax/ 不出现内部类名；architecture/ 可以出现但不逐行解释；subsystems/ 可以出现实现细节。

---

### B. 文档结构：骨架

**单篇文档骨架**：

```
标题（精确描述覆盖范围的名词短语）
├── 定位段（1-3句：本文是什么、给谁看、覆盖什么）
├── 核心概念（读者必须建立的心智模型）
├── 主体内容（按读者认知顺序，非按代码文件顺序）
├── 约束与限制（读者必须知道的边界）
└── 深入指引（可选：指向更细节的文档，非必须阅读）
```

**渐进披露（倒金字塔）**。最重要的信息在最前面。读者可能只读第一段就离开——第一段必须传达核心。读者可能只读标题就停止——每个标题本身必须是信息性的。如果一个读者只有 30 秒，他至少应能获取本文的核心不变量。

**章节是论证链的环节**。每章回答一个明确的问题，章节间存在逻辑推进关系（递进 / 并列 / 总分 / 对比）。章节标题是名词短语（回答"什么"），不是动词短语（"实现X"）。不按代码文件顺序排列。

**信息密度有节奏**：章节开头低密度（建立方向）→ 核心论述高密度（规则、表格）→ 示例中密度（呼吸空间）→ 边界中低密度。全文高密度无喘息是反模式；全文低密度（水）也是。

---

### C. 段落与行文：肌肉

**段落是最小论证单元**，不是"几句话的集合"。三要素：

1. **主题句**（第一句）：声明本段要建立的一个事实。仅读此句即可获取核心信息。
2. **支撑**（中间）：解释机制、给出约束、提供示例。不引入新论点。
3. **收束**（可选末句）：点明边界、例外、或引出下一段的问题。

检验：遮住中间和末尾，仅读第一句——若无法判断"这段在讲什么"，主题句不合格。

**行文四规则**：

| 规则 | 说明 |
|------|------|
| 陈述式，非探索式 | 陈述已确定的事实，不记录探索过程 |
| 现在时态，非历史时态 | 描述当前状态，不描述演变。变更历史属于 git |
| 主动语态，明确主语 | "编译器发出错误"而非"错误会被发出" |
| 精确且完备 | 精确 = 读者能据此判断自己的代码是否合规；完备 = 不存在需要猜测的隐含条件 |

**术语管理**：首次出现时一句话定义，后续不重复。一词一义，一义一词。代码标识符（`IbFileHandle`）与散文术语（"文件容器"）对应但不混用。

**设计理由的书写**遵循"约束 → 决策 → 后果"三段式：因为 [不可改变的外部条件]，系统选择 [具体方案]，这意味着 [读者需要知道的行为影响]。不写探索过程（"试了A不行又试了B"），不写无约束的决策（"使用协议驱动"——为什么？），不写无后果的约束（"因为性能"——所以对我有什么影响？）。

**表格 vs 散文**：多个对象具有相同属性维度（平行对比）→ 表格。单个概念的因果链解释 → 散文。信息是枚举性的 → 表格。信息是推导性的 → 散文。表格列数不超过 5。

**示例设计**：最小充分（只含说明当前论点所需的最少元素）；配对出现（正面 + 反面）；注释说明意图（"为什么选择这种写法"），不解释代码做了什么。规则反直觉时先示例后规则（归纳）；规则自然时先规则后示例（演绎）。

**可读性约束**：

| 维度 | 约束 |
|------|------|
| 句子 | 单句不超过 40 字（中文）。超过则拆分 |
| 段落 | 不超过 8 句。超过则检查是否混入第二个论点 |
| 嵌套 | 列表嵌套不超过 3 层。超过则拆为独立小节 |
| 代码块 | 文档中代码片段不超过 20 行。超过则考虑引用源文件 |
| 表格 | 列数不超过 5。超过则拆分或改用散文 |
| 单篇长度 | 超过 500 行时审视是否应拆分 |

### D. 条目格式模板：骨骼

技术手册中大量出现"平行小节"——每个小节对一个特定的 API、类型、协议、模块作说明。这些平行小节必须遵循**严格一致的格式模板**，使读者建立阅读预期后能快速定位信息。

**函数/API**：签名 → 一句话说明 → 参数表 → 返回语义 → 约束/前置条件（如有）→ 错误/诊断码（如有）→ 示例（正面+反面）。

**数据类型**：一句话定位 → 继承/组合关系 → 字段表 → 核心不变量（2-5条）→ 与其他机制的交互（如有）→ 示例。

**协议方法**：一句话职责 → 签名 → 调用时机 → 契约（实现者保证什么 / 调用者依赖什么）→ 默认行为（如有）→ 示例。

**技术模块**：一句话定位 → 职责边界（做什么/不做什么）→ 对外接口表 → 内部结构（如需）→ 与其他模块的关系 → 约束。

**诊断码**：一句话说明 → 精确触发条件 → 严重级别 → 修复方式 → 示例（触发代码 + 修正代码）。

**一致性原则**：同一文档内所有平行小节必须使用同一模板。槽位要么填写要么整行省略，不得留空或写"无"。一句话说明必须是完整陈述句。表格列数在同一文档内保持一致。

**模板骨架速查**：

```
函数/API                          数据类型
─────────────────────────────     ─────────────────────────────
### `名称`                        ### 名称
签名（参数 → 返回）                一句话定位（是什么、在体系中的角色）
一句话说明。                       继承/组合关系
**参数**：| 参数 | 类型 | 说明 |   **字段**：| 字段 | 类型 | 语义 |
**返回**：语义说明。               **核心不变量**：（2-5条）
**约束**：（如有）                 **与其他机制的交互**：（如有）
**错误**：诊断码 + 触发条件        **示例**：构造 + 基本使用
**示例**：正面 + 反面

协议方法                          技术模块
─────────────────────────────     ─────────────────────────────
### `__方法名__`                  ### 模块名
一句话职责。                       一句话定位（解决什么问题）
**签名**：输入 → 输出             **职责边界**：做什么 / 不做什么
**调用时机**：谁在何时调用         **对外接口**：| 接口 | 说明 |
**契约**：实现者保证 / 调用者依赖  **内部结构**：（如需）
**默认行为**：（如有）             **与其他模块的关系**
**示例**：一个具体实现片段         **约束/限制**

诊断码
─────────────────────────────
### `DIAGNOSTIC_CODE`
一句话说明（何时产生）。
**触发条件**：精确规则（无歧义判断）。
**严重级别**：ERROR / WARNING。
**修复方式**：如何消除。
**示例**：触发代码 + 修正代码。
```

### E. 红线：禁止书写的内容

| 禁止 | 原因 |
|------|------|
| 过程叙述（"经过讨论/验证/实测..."） | 读者只需结论 |
| 历史演变（"旧X已删除，现为Y"） | 属于 git 历史 |
| 日期戳 / 完成标记（"已解决"、"已落地"、"最后更新：..."） | 文档正确则不需时间证明；不正确则时间不能拯救 |
| 未实现的设计（除非独立"规划"章节且明确标注） | 文档描述当前真实行为 |
| 任务编号 / 里程碑代号 / PR 编号 | 对读者是噪音 |
| 代码的散文翻译（逐行解释代码做了什么） | 代码自己会说 |
| 核查记录 / 验证清单 / 进度表 / 状态追踪 | 过程产物，属于 git 或 `tasks_docs/` |
| 只有作者能理解的缩写/代号 | 用描述性名称替代 |
| 混合抽象层级（用户语法和编译器内部类名同段出现） | 读者无法确定自己在哪个层级思考 |
| 过时信息 | 比没有信息更危险 |
| 未标注的假设 | 读者无法判断自己是否具备理解条件 |

### F. 引用与代码片段：工具

**引用是补充，不是替代**。删掉引用后当前段落必须仍然可理解。若删掉后信息量归零，说明当前文档缺少自己的叙述——修复方式是补全叙述，而非保留引用。引用的正确用途："本机制的完整形式化定义见 X"（当前已给出足够理解的摘要）。不用行号（用模块路径+类/函数名、章节名、或概念名）。不引用已删除/重组的路径。不引用内部工作文档。FAQ 必须附着于其所澄清的文档。

**代码片段三条件**（必须同时满足）：有上下文说明（在做什么、为什么出现）；自包含（不需打开源文件即可理解）；必要（自然语言无法同等精确表达）。做不到则删除，改用自然语言。

**代码注释与文档的边界**：对"正在修改这行代码的人"有用的信息是注释（局部设计意图、已知陷阱、不变量声明）。对"使用这个系统的人"或"理解这个设计的人"有用的信息是文档（完整机制、概念模型、使用指南）。

### G. 质量检验：验收

**段落级**：遮住段落中间和末尾，仅读第一句——能否判断"这段在讲什么"？

**文档级（5 分钟测试）**：一个具备基本背景知识的新读者，花 5 分钟阅读本文后，能否：(1) 说出本文覆盖什么、不覆盖什么；(2) 说出核心不变量（1-3 条）；(3) 知道在哪里找到更细节的信息；(4) 不会基于本文做出错误的使用决策。任何一条不满足则文档不合格。

**体系级**：本文描述的概念，其归属文档是否是本文？是否存在另一处部分复制了同一内容？删掉所有引用后本文是否仍然自包含？
