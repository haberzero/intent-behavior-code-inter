# 07 Goal 机制 — 目标生命周期（去插件化）

> 本文把"目标驱动运行"的机制从任何插件依赖中**解耦**，描述为一个**声明式协议**：目标怎么设定、怎么记录、怎么推进、怎么停止、怎么交接——全部落到任务控制文档上，由智能体按协议执行。**不需要任何插件能力**。

## 一、目标机制的本质

目标（Goal）不是一个工具状态，而是**一份可观察、可追溯、可验收的承诺**。它包含：

| 要素 | 内容 | 记录载体 |
|------|------|---------|
| **目标声明** | 要达成什么（可验收的最终状态） | 任务控制文档（NEXT_STEPS 或决策记录） |
| **任务序列** | 分解为可执行子任务（按序、依赖驱动） | NEXT_STEPS 当前主线块 |
| **工作原则** | 自主推进/交付纪律/重构授权/上报阈值 | AGENTS.md + 交接文档 |
| **硬性定时**（可选） | 截止时间；到达即停 | 目标声明头部 |
| **进度** | 每个子任务完成状态 | NEXT_STEPS + WORKLOG |
| **停止条件** | 何时算完成 / 何时算受阻 | 目标声明 + 停止条件段 |
| **交接** | session 边界的状态快照 | 交接文档 |

## 二、目标生命周期（五阶段）

### Phase A 设定
- 把目标写成**可验收的最终状态**（不是"努力方向"），分解为按序子任务（依赖驱动，先定依赖再定被依赖项）。
- 记录硬性定时（可选）：截止时刻 + "到达即停，不以'快完成了'为由超时"。
- 记录工作原则（自主推进/决策纪律/交付纪律/重构授权/分支政策/日志）。
- 记录停止条件（什么算完成 / 什么算受阻）。
- 落点：NEXT_STEPS 当前主线块 + 决策记录。

### Phase B 推进
- 每个子任务按 code-workflow 执行，完成即更新 NEXT_STEPS + WORKLOG。
- 每个子任务完成做描述性 commit（说明 + 验证计数）。
- 自动接续下一子任务（除非触及上报阈值）。

### Phase C 阻塞判断
- 先穷尽自主手段（反思/质询/分析/记录）。
- 仅当确实无法自主决定（用户意图不明穷尽无解 / 需用户裁决语义 / 与工作模式定论冲突 / 破坏性重构无法确认边界且独立分支也无法确定路线）才停止并上报（记录 blocker + 建议）。

### Phase D 完成/停止
- **完成**：最终状态已达成且有证据（对照目标声明逐项验收）。
- **受阻**：无法推进且有具体 blocker。
- **硬性定时到达**：无论进度如何，立即停止，汇报进度/未完成项/建议，等待用户。**不以完成/受阻归因，只停止运行等待用户。**

### Phase E 交接
- 若 session 过长或需换 session：写交接文档（见 06_handoff.md），包含当前状态 + goal objective 模板 + 待决项。

## 三、目标状态判定（完成 vs 受阻 vs 暂停）

| 状态 | 判定 | 动作 |
|------|------|------|
| **完成** | 目标声明的最终状态已达成，且有可验证证据（逐项对照） | 记录完成证据；清理临时文档；交接 |
| **受阻** | 存在具体 blocker（外部输入缺失 / 无法推进） | 记录 blocker + 建议；上报用户 |
| **暂停** | 非阻塞原因停止（用户暂停 / 定时到达 / 任务切换） | 记录进度快照；写交接 |
| **进行中** | 尚未达成最终状态，仍在推进 | 持续更新 NEXT_STEPS + WORKLOG |

**判定纪律**：
- 不因"工作难/慢/未完成/需澄清"就判受阻——受阻必须是真的无法推进（缺外部输入）。
- 完成必须有证据，不靠意图/部分进度/记忆。
- 暂停不归因为完成或受阻。

## 四、goal 与任务控制文档的整合

goal 机制**不依赖任何插件**，它把插件提供的"自动续接/预算/截止"能力，转化为**智能体按文档协议自觉执行**：

| 插件能力（不依赖） | 协议化替代 |
|-------------------|-----------|
| 自动续接下一任务 | NEXT_STEPS 当前主线块记录任务序列，每完成一项按序读下一项 |
| 硬性定时停止 | 目标声明头部记录截止时刻，"到达即停"协议 |
| 预算/轮次上限 | 交接文档记录 max 轮次/预算，智能体自觉遵守 |
| 完成/受阻状态 | 本机制 §三 的判定纪律（智能体自查） |
| 跨 session 持久 | 交接文档 + 任务控制文档（git 承载） |

**核心**：目标是**文档上的承诺**，不是工具里的状态。智能体通过读写任务控制文档来"持有"目标。

## 五、goal objective 模板（可直接复制进任何执行配置）

```
【<主线名> · <模式>】主任务：<可验收的最终状态>（见 <决策记录指针>）。

一、主线任务（按序，依赖驱动）：
<子任务 A>（内容 + 验收标准）→ <子任务 B> → ...
每完成一个任务用描述性 commit 提交（说明+验证计数），同步更新任务控制文档，然后自动接续下一任务。

二、自主推进偏好（最高优先）：总体偏向无人值守，允许较大限度自我裁定与自我质询分析并尽可能推进。只有经过最大限度反思/质询/分析后仍确实无法彻底自主决定的内容才造成阻塞。凡能自主决断的一律自主决断并详尽记录决策依据（工作日志）。上报阈值统一为"尽可能自主推进"——先穷尽自主手段，确实无法决定才上报。决策纪律：可大胆激进选方案，底线=架构原则/代码质量原则/非妥协/非tricky/非临时兼容层/大方向主线。不因需拍板而停滞。

三、交付纪律：本地 commit；禁止 push 到远程（硬原则）——除非用户明确指示允许 push，否则一律禁止 git push 到任何远程仓库，push 不因"已授权自主运行"而默许，必须等用户显式授权。破坏性重构授权（硬原则）：符合一般工程经验/普适性/合理架构设计且经分析确实优于现有体系及已有代码时，哪怕设计已被文档记录也允许破坏性重构；不禁止修改已有代码，已有代码优先级低于架构正确性与设计统一一致；此类破坏性变更默认已授权自主推进，仅需详尽记录决策依据与工作内容。大范围破坏性重构分支政策（硬原则）：无法确认边界/危害程度的破坏性重构，100% 授权在其独立分支（不污染主开发分支与主干分支）任意实验；仅当独立隔离分支也无法确定技术路线时才阻塞；独立分支禁止直接合并，确认技术路线后仅允许手动单独更新主开发分支；永不触碰主干分支。工作日志：所有自主决策/质询分析/方案取舍/变化前后(实现+测试+文档)必须详尽记录在任务控制文档，"只记录，不断决"。

四、工作流：每任务 code-workflow Phase 0-5 + 质量门 + 全量测试零回归（命令见项目 AGENTS.md）。

五、主任务阻塞/暂停时的支线（按优先级，主任务解阻立即回主线；全部主线任务被阻塞时自主推进，不因等待而停滞）：
1) 质量维护/代码健康；2) 专项审计（独立分支）；3) 低优先级改进；4) 测试体系重构。
每条支线仍须每批全量测试零回归、commit+留痕（仅本地）、遇上报阈值项即停。

六、停止条件：先穷尽自主手段（反思/质询/分析/记录），仅当确实无法自主决定时（用户意图不明穷尽无解/需用户裁决语义/与工作模式定论冲突/破坏性重构无法确认边界且独立隔离分支也无法确定技术路线）才停止并记录 blocker。凡能自主决断的一律自主推进并记录工作日志。（破坏性重构默认已授权，仅在独立分支也无法确定路线时才阻塞。）硬性定时到达即停止并汇报，不以完成/受阻归因，只停止运行等待用户。

七、非目标：<明确不做的事>。
```
