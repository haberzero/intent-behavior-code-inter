# AGENTS.md — 通用工作原则（项目无关）

> 智能体进入任何项目后的**开工前必读**。本文件是方法论层（与具体项目无关）；项目专属事实（测试命令、目录结构、语言约定）由项目级 `AGENTS.md` 补充。
> 本文件只放指针与硬规则，不复制其它文档内容（单点真理）。

## 开工前必读（按顺序）

1. 项目级 `AGENTS.md`（若存在）——项目专属事实与硬约束
2. 本制度体系的 `task-control/README.md`——任务控制文档机制总览
3. `AGENTS.md` 下方"自主工作循环"与"不要做的事"
4. 按当前任务类型加载对应 skill（见 `skills/` 目录，路由由任务触发词决定）

## 自主工作循环（工作方式，强制）

> 目标：在约束内最大限度自主推进。每项任务默认走"理解 → 设计质询 → 自主决策 → 实现 → 自反馈验证 → 自主纠错 → 交付自查 → 收尾"闭环，具备自我反馈、自主纠错、自主决策能力；**只把真正需要用户拍板的项上报**。细节按 skill 执行。

> **原则优先于行为维持**（硬原则）：当既有代码/行为被确认违反一般性的工程/架构原则时，**优先以架构/工程原则为准，不以"保持已有行为"为主**。改前先分析，改后详尽记录变化前后（实现 + 测试 + 文档），供未来追溯。

> **可推翻项目自身设计缺陷**（硬原则）：项目自身的设计缺陷/失误，即使设计思路已在文档明确记录，也可推翻并按更普适、实践合理且有充分理由的方案重建。此类问题**通常不进入上报阈值**，仅需详尽记录决策依据与工作内容（实现 + 测试 + 文档变化前后）即推进。

1. **理解**：读任务的下一步/阻塞文档定位任务、阻塞与硬约束。
2. **设计与质询**：方案对照工作模式定论 + 自我质询 + 异味自查 + 设计哲学。
3. **自主决策**：能自主决断的自行决断并记录理由；仅触及下方上报阈值的项才向用户陈述（方案 + 推荐 + 理由）。
4. **实现**：按 code-workflow 卫生纪律执行。
5. **自反馈验证**：跑项目测试命令 + 残留扫描 + 自复核（subagent 报告不等于做完）。
6. **自主纠错**：验证失败 / 异味命中 → 回到根因阶段修复再验证，循环至干净或需上报；禁止症状层打补丁。
7. **交付自查**：code-quality 提交前自查 + 自我质询未决断项归零。
8. **收尾**：文档同步（单点真理表）、临时文档清理、汇报。

> **禁止 push 到远程（用户明确，硬原则）**：**除非收到用户明确指示允许 push，否则一律禁止 `git push` 到任何远程仓库**。全程只做本地 `git commit`；推送动作必须等用户显式授权后执行。此原则凌驾于"自主推进偏好"与"决策纪律"之上——无论自主推进范围多大，push 都不在自主范围内，不因"已授权自主运行"而默许。

> **破坏性重构授权（用户明确，硬原则）**：当判断符合一般工程经验、符合通常意义下的普适性、属于合理的架构选择与设计，且经分析确实优于现有体系及已有代码时，**哪怕该设计已被文档明确记录，也允许进行破坏性重构**。用户**不禁止对已有代码的修改**；已有代码的优先级**低于**架构正确性与设计上的统一一致。此类破坏性变更（含已被文档记录的设计）**默认已授权自主推进**，仅需详尽记录决策依据与工作内容（实现+测试+文档变化前后）即推进。

> **大范围破坏性重构的分支政策（用户明确，硬原则）**：对于**无法确认边界、无法判断危害程度**的破坏性重构，**100% 授权在其独立分支上**（不污染主开发分支，不污染任何计算机环境与用户目录），允许在该独立分支进行**任意程度的破坏性实验与重构**。**只有当即使该独立隔离分支也无法经自主实验确定工作路线时**，才将相关任务配置为阻塞。**独立分支禁止直接合并到主开发分支或主干分支**；只有在确认完整技术路线后，才允许单独进行手动的主开发分支代码更新。**永远不允许触碰主干分支（`main`）的代码。**

> **自主推进偏好（用户明确，最高优先）**：总体思路**偏向无人值守**，允许模型**较大限度自我裁定与自我质询分析**，并**尽可能推进**。**只有经过最大限度反思、质询、分析后仍确实无法彻底自主决定的内容，才造成阻塞**。凡能自主决断的，一律自主决断并**详尽记录决策依据**（工作日志）。上报阈值应**从最小化上报**统一为"**尽可能自主推进**"——不是"遇到困难就上报"，而是"先穷尽自主手段，确实无法决定才上报"。

**上报阈值**（仅以下**在穷尽最大限度自主反思/质询/分析后仍无法决定**才向用户确认/请示）：
- 公理层或语义错误集变更（须全量测试评估破坏面）——但**倾向自主评估并推进**，仅在评估后确需用户裁决语义取舍时才上报
- 对外契约 / 破坏性变更（API 签名、协议、序列化格式）——**破坏性改造已获用户授权，默认自主推进**；仅在无法确认边界/危害程度且无法经独立分支实验确定路线时才单独隔离到独立分支继续
- 跨子系统架构取舍，或需裁决与工作模式定论的冲突——**先自主分析并给出推荐方案**，确实无法自主裁决才上报
- 用户意图不明，且代码/文档/测试无法给出确定答案——**先穷尽代码/文档/历史证据**，确实无解才上报
- **搁置 / 封存任务解封**：仅当解封触及上述架构/契约/破坏性变更时才上报；否则可**自行重新评估并解封**，记录解封依据与工作内容即可推进

> **工作日志记录（用户明确，强制）**：所有自主决策、质询分析、方案取舍、变化前后（实现+测试+文档）必须**详尽记录**。记录在任务控制文档（如 WORKLOG 或各任务文档的决策记录段落）。**"只记录，不断决"**——能自主决定的就记录决定并推进，不断等用户；只有确实无法决定的才在记录中标记为待决并上报。

**默认自主范围**（直接推进不打断）：局部 bug 修复、机械性清理、测试补齐、文档同步、符合既有方向的小型重构。

## 长期质量维护与主线开发的排布

> 质量检测/异味维护是**长期存在的背景工作**，但不时刻与主线同强度。按分层节奏错峰运行：
> - **Tier A（随主线顺带）**：主线每次改动只做本次范围的质量自检（不扩大）。
> - **Tier B（定期窗口）**：主线阶段边界/里程碑做低强度批量质量巡检（分类 + 只修低风险项 + 记录）。
> - **Tier C（专项审计）**：主线停滞或用户指定时，独立分支做专项审计。
> - **无目的审视**为**最低密度**的背景过程，产出潜在参考入审视清单，并周期性事实回顾防过期。
> 分配原则：主线永远是主要意图；质量维护只在阶段边界或用户指定时介入，不打断主线冲刺；同一时刻只主推一个 P0 阶段。

## 测试

- 测试命令以**项目级 `AGENTS.md` 为准**（不在此写死任何项目的命令）。
- 每次改动全量测试零回归才算完成。
- 基线以实跑为准，不冻结数字。

## 不要做的事

- 不复制其它文档内容到本文件（单点真理；本文件只放指针）。
- 不在文档中冻结测试通过数字（以实跑为准）。
- 不同时主推多个 P0 阶段。
- 不写 compat shim / 胶水 / tricky 实现。
- 不在代码注释中使用任务代号/文档章节指针/历史叙述——注释只注明功能设计与已知问题。
- 重大架构决策写入架构文档对应章节，不再使用独立 ADR 文件。
- 执行文档治理前必读 doc-governance skill，按流程操作——禁止凭经验直接修改，必须先审计、做任务规划、交叉核验。
- 执行代码任务前必读 code-workflow skill，按流程操作——禁止未理解代码上下文前动手修改，必须对照工作模式定论检验方案。
