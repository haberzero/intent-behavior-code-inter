# 自我质询（Self-Grill）

> 将 `grilling` 的拷问姿态从"我对用户发问"转向"我对自己发问"：在设计树每条分支、决策依赖、边界与假设上逐项自我质询，直到没有含糊之处；凡是能靠探索代码库/文档回答的，绝不留给用户；只有真正需要用户拍板的项才反馈。
> 目标：在交付前主动暴露**不清晰、不明确、未验证、未决断**的内容，而不是等复查时被问住。

## 一、质询范围（沿设计树逐项走）

1. **目标与范围**：要解决的问题边界是否清晰？验收标准是否可判？"完成"的定义是什么？
2. **决策依赖**：当前方案依赖哪些前置决策？这些决策定了吗？顺序对不对（先定依赖、再定被依赖项）？
3. **边界与异常**：空值 / 缺省 / 越界 / 并发 / 失败路径各自是什么行为？有没有"没想过"的输入？
4. **假设验证**：方案建立在哪些假设上（行为预期、性能、用户意图、现有代码的真实状态）？每条假设是否已被代码库证据证实？还是我"认为"的？
5. **取舍与代价**：每个取舍（时间 vs 质量、通用 vs 简单、兼容 vs 重构）有没有说明理由？理由成立吗？**当既有行为与一般性工程/架构原则冲突时，取舍是否以"原则优先于行为维持"为基准（而非迁就已有行为）？** 若按原则改变行为，是否详尽记录了变化前后供追溯？**若属项目自身设计缺陷（即使文档化），是否已按更普适+实践合理方案重建、并详记决策？**
6. **未决断项**：哪些地方我其实没拿定主意，只是默认/跳过了？哪些需要用户意图才能定？

## 二、质询方法

- **一次一个问题**：逐个消解，不要一次抛出多个（多个问题并存只会更混乱）。
- **能查就先查**：问题能被代码库 / 文档 / 测试回答的，先探索回答；只有探索后仍无确定答案的，才算"待决断"。
- **给推荐答案**：每个待决断项，先给出我的推荐与理由（参考 `grilling` 的姿态），供用户快速裁决。
- **区分层次**：与 `code-odor` 分工——`code-odor` 找"质量红旗"（异味信号），`self-grill` 找"任何不清晰"（含范围、语义、取舍、假设），覆盖更广。

## 三、输出：反馈给用户的待决断项

- **汇总**：把无法自主决断的项整理成列表，每项给出【问题、上下文、为什么无法自主、我的推荐 + 理由】。
- **按影响排序**：阻塞后续工作的、涉及架构/契约/破坏性变更的优先。
- **绝不虚构结论**：拿不准就是拿不准，不用"合理默认"掩盖未决断——把决定权交还用户。

## 四、与相关 skill 的分工

- `grilling`：对用户的拷问（用户主动要求被质询时；本 skill 是它的内向版本）。
- `code-odor`：异味特征定位与工作过程自查（针对质量红旗）。
- `code-quality`：判定与处置基准（红线 / 分类）。
- 本 skill 的产出是"待决断项清单"，不是实现或判定。
