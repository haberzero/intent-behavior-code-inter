# 代码复核与验证工作流

> 本 skill 规范 AI 智能体在 IBCI 项目中执行**缺陷复核、分类决策、实施后核验**的工作流程。与 `code-workflow`（管"怎么实现"）互补：code-review 管"怎么验证和决策"。
>
> 核心原则：**代码是最高真相。二手报告不可盲信。矛盾必须用直接证据裁决。**

---

## 一、工作流程总览

```
Phase 0: 独立验证（并行 subagent 核实每条断言）
Phase 1: 分类先行（判定每项的正确处置动作）
Phase 2: 严格分组（三重标准检验是否可合并讨论）
Phase 3: 决策准备（完整叙述 + 证据引用 + 建议）
Phase 4: 实施后核验（残留扫描 + subagent 遗漏检查 + 文档同步）
Phase 5: 规则永久化（治理文档更新 + 自查工具）
```

**与 code-workflow 的关系**：Phase 0-3 是 code-workflow Phase 0（理解任务上下文）的前置深化；Phase 4-5 是 code-workflow Phase 4-5（测试与收尾）的后置深化。当任务包含"验证已有缺陷记录"或"批量代码变更后的核验"时，使用本 skill；当任务仅为"实现明确需求"时，直接使用 code-workflow。

---

## 二、各阶段详述

### Phase 0: 独立验证

**输入**：缺陷报告、问题清单、或任何声称"代码中存在 X 问题"的记录。

**关键原则**：禁止直接按记录修复。每条断言都必须对照实际代码独立验证。

**动作**：

1. **检查跨 session 冲突**：`git fetch && git log --oneline origin/<branch> -5`，确认是否有其它 session 的新提交。如有，读取其 diff 确认与计划工作无冲突（行号偏移、文件重叠）。

2. **启动并行 subagent 做独立验证**。每条缺陷分配验证任务，subagent 需要：
   - 读取缺陷记录中标注的代码位置（file:line）
   - 核实每条断言是否属实（位置准确？描述的代码行为存在？严重性评估合理？）
   - 查阅设计文档确认设计意图（缺陷描述的"问题"是否就是设计意图？）
   - 查阅测试确认覆盖情况
   - 返回结论：✅属实 / ⚠️部分属实 / ❌不实

2. **矛盾裁决**。当两个 subagent 报告矛盾时：
   - **不靠"谁更可信"裁决**--亲自读取代码获取直接证据
   - 用 grep/Read 工具直接确认事实（如"是否有调用点"用 grep 计数）
   - 记录矛盾原因和裁决证据

3. **验证记录的真实性**。特别警惕以下陷阱：
   - **陈旧文档**：文档描述与代码现状不符（如 KNOWN_LIMITS 说"未启用"但代码实际已接通）
   - **前提错误**：记录基于不存在的前提（如"get_value 方法"实际从未存在）
   - **过度定性**：记录定性为 CRITICAL 但实际影响有限（如竞态只污染诊断不污染执行结果）
   - **混淆"死代码"与"预留接口"**：死代码应删除，预留接口应激活，误判导致错误动作

**输出**：每条缺陷的验证结论（属实/部分属实/不实）+ 证据（file:line + 代码片段）+ 矛盾裁决记录。

### Phase 1: 分类先行

**输入**：Phase 0 的验证结论。

**关键原则**：分类决定动作。误分类导致错误动作。

**动作**：

对每项已验证的问题，判定其类别：

| 分类 | 定义 | 正确动作 | 误判后果 |
|------|------|---------|---------|
| **真 bug** | 代码行为与设计意图不符 | 修复 | -- |
| **死代码** | 代码存在但永远不执行（零调用点、前提不存在） | 删除 | 当"预留接口"误判为"死代码"会丢失设计 |
| **有效死代码** | 当前不可达（约束保证不执行），但约束变化后可变为可达 | 改为 fail-fast 断言（raise），消除 latent defect | 保留=潜伏 bug；删除=丢失防御；断言=正确 |
| **功能空壳** | 代码存在、有调用点但核心逻辑为空（如 `pass`/返回常量） | 删除（违反架构原则时）或实现（有未来需求时） | 保留空壳=保留技术债 |
| **半接通特性** | 框架已落地但职责分离未完成（如调度机制在但安全隔离未做） | 禁用默认路径 + 并入专项重做 | 局部修补=在不稳固的地基上加盖 |
| **预留接口未激活** | 字段/方法已声明、有设计意图、但无消费者 | 激活（添加消费者、修复类型契约） | 当"死代码"误判为"预留接口"会保留垃圾 |
| **设计限制** | 不是 bug，是设计决策的后果 | 文档化到 KNOWN_LIMITS | 修复"设计限制"浪费资源 |
| **需讨论** | 无法从文档/原则/代码单独决断 | 进入 Phase 2-3 准备决策材料 | -- |

**分类的验证方法**：
- "死代码"vs"预留接口"：grep 全仓库是否有消费者 + 查 git 历史是否曾存在消费者 + 查设计文档是否有未来计划
- "真 bug"vs"设计限制"：查 KNOWN_LIMITS 和架构文档，确认行为是否被文档化为设计决策
- "半接通"vs"完整实现"：查 VM_SPEC 等规范文档，确认设计意图与实现的差距

**输出**：每项的分类 + 分类依据 + 建议处置动作。

### Phase 2: 严格分组

**输入**：Phase 1 的分类结果 + 需讨论项清单。

**关键原则**：只有三重标准完全一致的项才能合并讨论。宁可全部独立也不强行关联。

**动作**：

1. **检验每个候选组的三重标准**：

   | 标准维度 | 检验内容 | 示例 |
   |---------|---------|------|
   | **问题本质** | 从架构/长远设计看，问题的根源是否相同？ | "快照保护不完整"和"编译检查不完整"虽然都关于隔离，但根源不同（存储模型 vs 编译检查） |
   | **修复方案** | 修复的代码改动方式是否一致？ | "加 grep 扫描"和"改 AST 节点覆盖"是不同方案 |
   | **架构层级** | 改动发生在同一架构层吗？ | "运行时存储模型"和"编译器语义分析"是不同层 |

2. **三重标准全部一致 -> 可分组**。任何一项不一致 -> 独立。

3. **常见误判**：
   - "同在一个文件"-> 不等于可分组（同文件不同函数解决不同问题）
   - "同属一个主题"-> 不等于可分组（"隔离"主题下有策略层/存储层/编译层三个独立问题）
   - "修复 A 会减少 B 的风险面"-> 不等于可分组（修复 A 不消除 B 的缺口）

4. **即使全部独立也要明确报告**：说明检验了哪些候选组、为什么不满足分组标准。这向用户确认"没有遗漏潜在的架构关联"。

**输出**：分组结论（N 组独立项 / 每组包含哪些项 / 检验过的候选组及排除理由）。

### Phase 3: 决策准备

**输入**：Phase 2 的分组结果 + 每组的分类与建议。

**关键原则**：决策者必须先充分理解问题才能做决策。不能直接跳到"选 A 还是 B"。

**动作**：

对每个需用户决策的组（或独立项），准备完整的决策材料：

1. **完整叙述**（7 个维度）：

   | 维度 | 内容 |
   |------|------|
   | 问题是什么 | 用一句话描述问题的核心矛盾 |
   | 从哪里来 | 问题的发现背景（谁/何时/在什么场景下发现的） |
   | 本质是什么 | 从架构/设计角度看，这是哪类问题（参考 Phase 1 分类） |
   | 最初的设计思路 | 设计时这段代码/接口的意图是什么（引用设计文档） |
   | 涉及哪些代码 | 具体的 file:line + 关键代码片段 |
   | 与现有约束的关系 | 与 KNOWN_LIMITS / 架构原则 / VM_SPEC 公理的关系 |
   | 在 pending 工作中的位置 | 与 PENDING_TASKS 中已有项的关系（是否重复/包含/独立） |

2. **检验"不迁就现状"维度**：
   - 方案是否因"但现在就是这么工作的"而保留了糟糕设计？
   - 类型标注是否诚实（如 `Optional[List[str]]` 隐藏了 bool 语义）？
   - 是否存在隐式约定（如 `None` = "全部"需要查文档才能理解）？
   - 如果推翻现状重设计，是否更易懂、更易维护、更可扩展？

3. **检验半修复风险**：
   - 方案是否涉及多个必须同修的点？（如"加 setter" + "清死分支" + "清 setattr" 三处同修）
   - 只修一处是否会遗留"旧路径 + 新路径并存"的双通道？
   - 明确列出所有必须同修的文件和改动点，确认方案覆盖全部
   - 半修复（只修症状不修根因、只修一处不修级联）禁止

4. **给出建议**（不是选项）：
   - 给出推荐方案及理由，而非"选 A 或 B"
   - 如果推荐方案需要更大改动，明确说明"改动更大但设计更正确"
   - 不提供"最快速修复"建议，除非快速修复本身就是最佳方案

5. **确认方向后再进入实现**：用户的确认是对问题理解的确认，不是对"选 A 还是 B"的确认。

**输出**：获批的方案方向 + 理解确认。

### Phase 4: 实施后核验

**输入**：已完成的代码修改（可能是自己实施或 subagent 实施）。

**关键原则**："subagent 说做完了"不等于"做完了"。必须独立验证完整性。

**动作**：

1. **残留扫描**：
   - 用 grep/Python 脚本扫描所有应被替换/删除的旧模式
   - 扫描范围必须**超出 subagent 的分配范围**（subagent 可能遗漏范围外文件）
   - 示例（注释清洁后）：
     ```bash
     grep -rnE 'ADR-[0-9]|PT-ARCH|PT-[0-9]|Per ADR|§[0-9]|tasks_docs/' --include='*.py' core/ tests/
     ```
   - 示例（诊断码替换后）：
     ```bash
     grep -rnE '"(SEM_[0-9]{3}|PAR_[0-9]{3}|LEX_[0-9]{3})"' --include='*.py' core/
     ```
   - 确认零残留后才提交

2. **subagent 遗漏检查**：
   - 对照 subagent 报告的"已处理文件清单"，逐一确认修改确实落地
   - 检查 subagent 报告的"跳过/不确定"项是否需要补处理
   - 检查是否有文件不在任何 subagent 的分配范围内但包含目标模式

3. **文档同步检查**：
   - 代码变更是否需要同步更新 KNOWN_LIMITS？
   - 代码变更是否需要同步更新架构文档（04_vm_interpreter / 05_vm_specification）？
   - 代码变更是否需要同步更新语法文档？
   - 诊断码变更是否更新了 docs/README.md §三.6 的保留例外列表？

4. **测试验证**：
   - 运行 `python -m pytest tests/`
   - 测试断言引用旧码字符串时需同步更新（这是改革的必要组成部分，不属于"测试用例重构"）
   - 确认 pass/fail 计数与基线一致（除非有预期的 skip 变化）

5. **差距分析**：在"已修复"和"扫描结果"之间做差距分析。每条遗漏都需要明确理由（"合理豁免"或"补修"）。

**输出**：零残留确认 + subagent 遗漏补修 + 文档同步更新 + 测试通过报告。

### Phase 5: 规则永久化

**输入**：Phase 4 核验通过后的变更。

**关键原则**：一次性清洁/修复不够。规则必须写入治理文档，使未来代码始终遵循。

**动作**：

1. **识别本次变更中产生的通用规则**：
   - 注释清洁 -> 注释卫生纪律
   - 诊断码整改 -> 诊断码使用规则
   - 字段类型修复 -> 类型标注诚实原则

2. **写入治理文档**：
   - 代码层面的规则 -> `docs/README.md` §三（文档治理纪律）
   - 硬规则 -> `AGENTS.md` "不要做的事"
   - 工作流层面的规则 -> 本 skill 或 code-workflow skill

3. **提供自查工具**：
   - 给出具体的 grep 命令供未来开发者自查
   - 命令应覆盖本次发现的所有违规模式

4. **更新 AGENTS.md 指针**（如有新增 skill 或文档章节）

5. **清理临时任务文档**：经用户确认后删除 `tasks_docs/_*.md`。完成状态由 git 提交历史承载。

**输出**：更新的治理文档 + 自查工具 + 清理的临时文档。

## 三、关键模式

### 3.1 矛盾裁决

**场景**：两个独立分析对同一事实给出矛盾结论。

**裁决顺序**：
1. **源代码**（`core/` 中的实际逻辑）是最高真相
2. 代码中无法直接确认的 -> 查找测试用例的行为
3. 测试也无法确认的 -> 查找设计文档（VM_SPEC / 架构原则）
4. 设计文档也无法确认的 -> 标记为"待验证"，不擅自裁决

**禁止**：
- 不靠"哪个 subagent 更可信"裁决
- 不靠"哪个报告更长/更详细"裁决
- 不在未获取直接证据的情况下选择一方

### 3.2 "死代码"与"预留接口"的辨别

**场景**：发现一个没有消费者的字段/方法，需要判断是删除还是激活。

**辨别方法**：
1. grep 全仓库是否有消费者（零消费者 -> 候选"死代码"或"预留接口"）
2. 查 git 历史：`git log -p --all -S "field_name"` -- 是否曾有消费者
3. 查设计文档：是否有未来计划使用此字段
4. 查类型契约：类型标注与实际赋值是否一致（不一致 -> 可能是"预留但未正确激活"）

**决策**：
- 无设计意图 + 无未来计划 + 无历史消费者 -> **死代码，删除**
- 有设计意图 + 有未来计划 + 类型契约破损 -> **预留接口，激活**

### 3.3 "不迁就现状"检验

**场景**：设计修复方案时，检查是否因惯性而保留了糟糕设计。

**检验问题**：
1. 如果从零开始设计这个接口，会用现在的方案吗？
2. 现在的方案中是否有"为了不破坏现有行为"而做的妥协？
3. 类型标注是否诚实地描述了字段的实际用法？
4. 是否存在需要查文档才能理解的隐式约定（如 `None` = "全部"）？
5. 如果推翻现状重设计，是否更易懂、更易维护、更可扩展？

**原则**：如果推翻现状的方案明显更优，推荐推翻。改动更大不是反对理由。

### 3.4 残留扫描的覆盖范围

**原则**：扫描范围必须**超出**实施者的分配范围。

**原因**：subagent 只处理分配给它的文件。目标模式可能出现在：
- 未分配给任何 subagent 的文件
- subagent 报告中标注"跳过"的文件
- 非代码文件（文档、配置）

**方法**：
1. 对整个 `core/` 和 `tests/` 目录做全量 grep
2. 对 `docs/` 目录做全量 grep（文档引用也需要同步）
3. 确认零残留后才提交

## 四、与其它 skill 的关系

```
code-review Phase 0-3（验证 + 分类 + 分组 + 决策）
    ↓ 输出：获批方案方向
code-workflow Phase 0-5（理解 + 读代码 + 设计 + 实现 + 测试 + 收尾）
    ↓ 输出：已实施的代码变更
code-review Phase 4-5（核验 + 永久化）
    ↓ 输出：零残留确认 + 治理文档更新
```

**何时用 code-review**：
- 拿到缺陷报告需要验证时
- 批量代码变更后需要核验完整性时
- 需要向用户准备决策材料时
- 需要将一次性清洁的规则永久化时

**何时用 code-workflow**：
- 需求明确，直接实现时
- 修复已验证的单一 bug 时
- 重构已确认方向代码时

**何时两者都用**：
- 复杂缺陷处置（先 code-review 验证+决策，再 code-workflow 实现，最后 code-review 核验）
- 大规模代码整改（先 code-review 分类+分组，再 code-workflow 批量实施，最后 code-review 核验+永久化）

## 五、硬约束速查

### 5.1 验证纪律

```
1. 不盲信二手报告（包括自己过去的分析）
2. 代码是最高真相
3. 矛盾必须用直接证据裁决
4. subagent 报告必须独立验证完整性
```

### 5.2 分类纪律

```
1. 分类决定动作（bug->修复 / 死代码->删除 / 预留接口->激活 / 设计限制->文档化）
2. "死代码"与"预留接口"必须用 git 历史 + 设计文档辨别
3. "半接通特性"不局部修补，禁用 + 并入专项
```

### 5.3 分组纪律

```
1. 三重标准：问题本质 + 修复方案 + 架构层级，全部一致才可分组
2. 不因"同文件"/"同主题"/"修复A减少B风险"而强行分组
3. 全部独立也要明确报告（确认无遗漏的架构关联）
```

### 5.4 决策纪律

```
1. 决策前完整叙述（7 个维度）
2. 检验半修复风险（级联依赖是否全部覆盖）
3. 给建议而非选项
4. 检验"不迁就现状"
5. 不提供"最快速修复"（除非快速修复本身就是最佳方案）
```

### 5.5 核验纪律

```
1. 残留扫描范围超出 subagent 分配范围
2. 零残留确认后才提交
```
