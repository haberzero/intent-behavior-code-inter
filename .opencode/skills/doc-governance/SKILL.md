# 文档治理工作流

> 本文档是 IBCI 文档体系的治理工作流规范。面向需要执行文档审计、格式治理、内容补充或体系建设任务的 AI 智能体。覆盖从初始评估到最终复查的完整流程、关键决策模式与可复用检查清单。

---

## 一、工作流程总览

文档治理遵循 8 个阶段，每个阶段有明确的输入、输出和完成条件：

```
Phase 0: 理解上下文
Phase 1: 写作指导自审
Phase 2: 全量健康检查（并行 subagent）
Phase 3: 汇总分析与任务规划
Phase 4: 分阶段执行治理
Phase 5: 交叉核验与遗漏修复
Phase 6: 读者视角评估
Phase 7: 体系建设与补充
Phase 8: 最终复查与清理
```

---

## 二、各阶段详述

### Phase 0: 理解上下文

**输入**：用户的任务描述。

**动作**：
1. 读取 `AGENTS.md`，理解项目的治理纪律和硬规则。
2. 读取项目的文档书写规范（IBCI 为 `docs/WRITING_GUIDE.md`）。
3. 读取文档体系导航文件（IBCI 为 `docs/README.md`），理解分层结构和阅读路径。
4. 确认任务范围：哪些目录/文件在管辖范围内，哪些明确排除。

**决策点**：如果项目没有书写规范，需先与用户确认是否要建立规范，再进入治理——治理需要"尺子"。

**输出**：对治理域（被检查的文件集）和规则集（检查依据）的清晰理解。

### Phase 1: 写作指导自审

**输入**：项目的书写规范文档。

**动作**：
1. 将书写规范的每条规则应用到书写规范自身，检查自洽性。
2. 逐条对照规则，寻找自我违规：
   - 文件身份是否匹配（§A.6：标题、定位段、内容一致否）
   - 定位段是否合规（§B.1：是否真正说明了"是什么、给谁看、覆盖什么"）
   - 红线禁令是否被自身违反（§E：日期戳、历史叙述、完成标记）
   - 示例设计是否配对（§C.6：正面+反面）
   - 主动语态（§C.2："应被显式设计"→"应显式设计"）
3. 参考外部成熟实践（Divio 文档四分法、Write the Docs 社区指南、Google 文档风格指南、Python/Rust 官方文档），对比规范是否完备，提出改进建议。

**输出**：书写规范自身的合规报告 + 改进建议清单。

### Phase 2: 全量健康检查（并行 subagent）

**输入**：规则集 + 需检查的文件清单。

**关键原则**：禁止抽检，必须全覆盖。每个文件都需通过同一套规则检查。

**动作**：
1. 按目录拆分任务，每个目录分配一个 subagent。典型拆分：
   - `docs/syntax/`（Reference 层）
   - `docs/architecture/`（Explanation 层）
   - `docs/subsystems/`（Explanation 层）
   - 顶级文档 + 索引手册
   - 额外一个 subagent 做**体系结构分析**（导航、读者旅程、跨文档一致性、概念归属）
2. 为每个 subagent 提供统一的检查标准——从书写规范中提取的规则清单：
   - §A.6 文件身份（标题/定位段/内容一致）
   - §B.1 单篇骨架（定位段→核心概念→主体→约束→深入指引）
   - §B.2 渐进披露（重要信息在前）
   - §B.3 章节标题（名词短语）
   - §C.7 可读性约束（行数、代码块行数、文件长度）
   - §E 红线（日期戳、历史叙述、任务编号、设计代号、过程叙述）
   - §D.2 格式一致性（平行小节模板统一）
   - §F 引用（删掉引用后段落仍可理解，路径有效）
   - 诊断码/公理码一致性：文档中引用的诊断码须与 `core/base/diagnostics/codes.py` 一致（命名制，如 `SEM_TYPE_MISMATCH`）；公理码须与 `docs/architecture/05_vm_specification.md §8` 公理注册表一致
   - §A.7 层间正交（跨层抽象泄漏）
3. subagent 报告格式要求：摘要表 + 逐文件详细发现 + 按规则分类汇总。
4. 体系结构分析的 subagent 额外检查：
   - 文档四分法覆盖（Tutorial/How-to/Reference/Explanation）
   - 概念归属唯一（跨文件重复描述）
   - 读者旅程完整性（断路点、死胡同）
   - 索引文档质量
   - 跨文件事实一致性

**输出**：每个 subagent 的结构化违规报告，包含文件路径、违规文本、违反的规则编号、严重级别。

### Phase 3: 汇总分析与任务规划

**输入**：所有 subagent 报告。

**动作**：
1. 合并所有 subagent 报告，去重，按规则分类汇总。
2. 将违规分为三个优先级：
   - **P0**（立即修复）：断链引用、事实矛盾、缺失核心结构（如定位段）
   - **P1**（本阶段修复）：红线违规清理、格式不一致、跨层抽象泄漏
   - **P2/P3**（后续推进）：超长文件拆分、模块补齐、体系建设
3. 区分"格式问题"（可机械修复）和"结构问题"（需设计和判断）。
4. 创建临时任务文档（如 `tasks_docs/_doc_health_governance.md`），记录：
   - 完整的发现清单（每条可勾选）
   - 分阶段修复计划
   - 执行进度追踪
5. **区分管辖范围**：明确哪些文档在治理范围内，哪些不在（如 `tasks_docs/`、`tests_docs/`）。

**决策点**：遇到事实矛盾时，以代码事实为准（如 `SEM_003` vs `SEM_TYPE_MISMATCH`——查 `core/base/diagnostics/codes.py` 确认）。

**输出**：优先级排序的修复任务清单 + 临时任务追踪文档。

### Phase 4: 分阶段执行治理

**输入**：任务清单。

**动作**：
1. 从最高优先级开始，逐项修复。关键词：**扎实推进，不跳过，不找借口**。
2. 修复断链引用：用实际文件路径替换已删除/重命名的路径。
3. 修复事实矛盾：读取源代码，以代码事实为准更新文档。
4. 补齐缺失元素：为每个文件添加定位段（1-3 句），遵守 WRITING_GUIDE §B.1 格式。
5. 分行执行大批量修改：如为 13 个 syntax 章节添加定位段，使用 subagent 并行处理。
6. 每完成一个阶段，更新临时任务文档中的勾选状态。
7. 修复书写规范自身的违规。

**输出**：所有 Phase 任务项已修复的文件 + 更新的临时任务文档。

### Phase 5: 交叉核验与遗漏修复

**输入**：已修复的文件 + 原始 subagent 报告。

**这是最关键的阶段——跳过此阶段是治理失败的首要原因。**

**动作**：
1. 重新通读书写规范全文——避免凭记忆遗漏细节。
2. 逐一对照原始 subagent 报告的每一条违规，在修改后的文件中验证是否已修复。
3. 运行自动化扫描，搜索残留的违规模式：
   ```bash
   # 日期戳和完成标记
   grep -rn '最后更新\|202[0-9].*[0-9].*[0-9]\|已实现\|已废弃\|已改善\|已解决' docs/ --include='*.md'
   # 任务编号和设计代号
   grep -rn 'PT-[0-9]\|PT-ARCH\|D[12]\b\|C[0-9]\b' docs/ --include='*.md'
   # 历史叙述标记
   grep -rn '旧的\|原先\|以前\|曾经\|不再\|目前' docs/ --include='*.md'
    # 断链引用（已知已删除的路径名）
    grep -rn 'IBCI_SYNTAX_REFERENCE\|ARCH_DETAILS\|ARCHITECTURE_PRINCIPLES' docs/ --include='*.md'
    # 旧编号制诊断码残留（已改为命名制，如 SEM_TYPE_MISMATCH）
    grep -rnE 'SEM_[0-9]{3}|PAR_[0-9]{3}|LEX_[0-9]{3}' docs/ --include='*.md'
   ```
4. 在"修复的文件"和"扫描结果"之间做差距分析。每条遗漏都需要有明确理由（"合理豁免"或"补修"）。
5. 补修遗漏项。
6. 重复步骤 3-5 直到扫描干净。

**输出**：遗漏修复的补丁 + "已修复/合理豁免/已知未修复"的完整分类。

### Phase 6: 读者视角评估

**输入**：治理后的文档体系。

**动作**：
1. 脱离"写作者"角色，以读者身份审视：
   - 一个 30 秒读者能从定位段获得什么？
   - 一个带着问题的读者 5 分钟内能找到答案吗？
   - 文档之间是否有合理的阅读路径，还是需要"猜测"？
2. 以技术写作者身份，评估体系层面：
   - 文档四分法是否完整覆盖（Tutorial/How-to/Reference/Explanation）？
   - 信息架构是否按读者旅程组织，而非按代码文件组织？
   - 跨文档信任度——同一事实是否在两处说辞不一？
3. 引用外部成熟实践（Python 官方 Tutorial、Rust Book、Write the Docs 原则）作为参照。
4. 给出明确的评价（可以打分）和改进建议——区分"现在能做的"和"需要前置条件的"。

**输出**：读者视角评价报告 + 分级改进建议。

### Phase 7: 体系建设与补充

**输入**：Phase 6 的评价 + Phase 0-5 的修复结果。

**动作**：
1. 对体系缺口提出建设方案：
   - 缺 Tutorial 层 → 新建教程目录，写分步教程章节
   - 缺 How-to 层 → 评估素材来源（语法参考 + 代码事实 + 通用入门经验是否足够）
   - 导航页过厚 → 截取为薄导航页，原内容归档或整合到新章节
2. 新建内容必须遵守与已有内容相同的书写规范——不能因为"新"而降低标准。
3. Tutorial 章节设计原则：
   - 每章以"你将会学到"开头，"你现在能做什么"结尾
   - 顺序推进，前一章是后一章的前置
   - 每条语法只给最小示例，完整规范引用 Reference 层
   - 在章节末尾的"下一步"指针中引用教程的下一章
4. 配套修改索引文件、导航页、书写指导中的相关引用。

**决策点**："先不要考虑内容本身的正确性"（用户指示）仅适用于格式治理阶段。体系建设阶段需要确保内容准确——教程中的每条代码示例都应在 MOCK 模式下可运行，诊断码应与源代码一致。

**输出**：新建的文档 + 修改的索引/导航文件。

### Phase 8: 最终复查与清理

**输入**：所有修改文件。

**动作**：
1. 重新通读所有新建/修改的文件（不能只扫标题）。
2. 验证导航链——教程的"下一步"指针是否形成完整闭环。
3. 验证格式一致性——同类文件是否使用相同的模板（标题级别、定位段格式、导航格式）。
4. 验证引用有效性——所有跨文档引用路径是否都存在。
5. 确认临时任务文档中所有任务项已勾选完成。
6. **向用户汇报治理结果**（完成项统计、未完成项及原因、后续建议）。
7. **清理临时任务文档**：经用户确认后，删除 `tasks_docs/_<task_name>.md`。临时任务文档是过程产物，不应长期留存——防止堆积污染项目目录。治理完成后的状态由 git 提交历史记录，无需保留临时追踪文件。
8. 如果有配套索引文件（如 AGENTS.md），同步更新。

**输出**：最终验证报告 + 已清理的临时任务文档。

## 三、关键模式

### 3.1 临时任务文档

**用途**：追踪治理全过程的进度，避免遗漏。

**创建时机**：Phase 3（汇总分析后，开始执行前）。

**格式**：
```markdown
# 文档体系健康治理任务清单

> 临时任务文档。治理完成后删除。

## Phase 1: 立即修复
### 1.1 断链引用修复
- [ ] `file.md` line N: `OLD_PATH` → `NEW_PATH`

### 1.2 事实矛盾修复
- [ ] `file.md` line N: `OLD_VALUE` → `CORRECT_VALUE`（代码事实）

## Phase 2: 深度清理
...

## Phase 3: 结构性问题
...
```

**位置**：`tasks_docs/_<task_name>.md`。下划线前缀 + 描述性名称。

**生命周期规则**（强制）：
1. Phase 8 核验完成后，**必须向用户汇报**治理结果概要。
2. 经用户确认后，**必须删除**临时任务文档。
3. 禁止保留已完成的临时任务文档——防止 `tasks_docs/` 目录堆积历史追踪文件，污染项目空间。治理完成状态由 git 提交历史承载。

### 3.2 并行 Subagent 审计

**用途**：在大规模文件检查中利用并行能力。

**拆分策略**：
- 按目录拆分（每个目录一个 subagent）
- 给每个 subagent 提供**相同的检查标准**（从书写规范中提取）
- 给每个 subagent 提供**统一的输出格式要求**（摘要表 + 逐文件详细 + 规则汇总）
- 额外的 subagent 处理跨文件的体系级分析

**Prompt 关键元素**：
1. 先读规范文档（`Read the WRITING_GUIDE.md first`）
2. 列出所有要检查的文件（`Read ALL files in directory/`）
3. 逐条列出检查项（`For EACH file, check...`）
4. 明确违规回报格式（`For each violation, report: file path, line number, specific text, rule violated`）
5. 要求结构化输出（`Return a structured report with summary table`）

### 3.3 自动化扫描

**用途**：Phase 5 交叉核验时，用 grep 快速发现遗漏的违规模式。

**扫描脚本模板**：
```bash
# 日期戳和完成标记
grep -rn '最后更新\|202[0-9].*[0-9].*[0-9]\|已实现\|已废弃\|已改善\|已解决' docs/ --include='*.md'

# 任务编号和设计代号
grep -rn 'PT-[0-9]\|PT-ARCH\|D[12]\b\|C[0-9]\b' docs/ --include='*.md'

# 历史叙述标记
grep -rn '旧的\|原先\|以前\|曾经\|不再\|目前' docs/ --include='*.md'

# 断链引用（已知已删除的路径名）
grep -rn 'IBCI_SYNTAX_REFERENCE\|ARCH_DETAILS\|ARCHITECTURE_PRINCIPLES' docs/ --include='*.md'
# 旧编号制诊断码残留（已改为命名制，如 SEM_TYPE_MISMATCH）
grep -rnE 'SEM_[0-9]{3}|PAR_[0-9]{3}|LEX_[0-9]{3}' docs/ --include='*.md'
```

**注意**：排除治理范围外的目录（`tasks_docs/`、`tests_docs/`、`backup/`）和规范文档自身（`WRITING_GUIDE.md` 中的示例文本）。

### 3.4 读者-作者双视角

**用途**：避免治理仅停留在"符合规则"层面，缺少"读者实际体验"的维度。

**执行方式**：
- 先以"作者"视角执行 Phase 0-5（规则驱动的机械化治理）
- 再以"读者"视角执行 Phase 6（体验驱动的人文评估）
- 两个视角天然互补——作者视角保证合规，读者视角保证可用

### 3.5 事实矛盾的裁决

**用途**：当不同文档对同一事实给出矛盾描述时，以什么为准。

**裁决顺序**：
1. **源代码**（`core/` 中的实际逻辑）是最高的真相
2. 代码中无法直接确认的 → 查找测试用例
3. 测试用例也无法确认的 → 标记为"待验证"并记录在临时任务文档中，不擅自修改

## 四、可复用检查清单

### 4.1 文档级健康检查清单（来自 WRITING_GUIDE §G.4）

```
- [ ] 有定位段（1-3句：本文是什么、给谁看、覆盖什么）
- [ ] 标题是名词短语，精确描述覆盖范围
- [ ] 定位段、标题、实际内容三者一致（§A.6）
- [ ] 无日期戳、无"最后更新"、无"已解决"标记
- [ ] 无历史叙述（"原实现采用..."、"经过讨论..."）
- [ ] 无任务编号（PT-xxx）、里程碑代号、PR 编号
- [ ] 无代码的散文翻译
- [ ] 段落不超过 8 句，单句不超过 40 字（中文）
- [ ] 代码片段不超过 20 行
- [ ] 文件不超过 500 行（超过则审视是否应拆分）
- [ ] 表格列数不超过 5
- [ ] 5 分钟测试通过（§G.2）
- [ ] 无跨层抽象混用（§A.7）
- [ ] 平行小节格式一致（§D.2）
```

### 4.2 体系级检查清单

```
- [ ] 文档四分法是否完整（Tutorial/How-to/Reference/Explanation）？
- [ ] 每个概念是否有唯一归属文档？
- [ ] 读者旅程是否有断路终点？
- [ ] 索引文档是否提供了有效的导航？
- [ ] 跨文档事实是否一致？（抽样 3-5 个关键事实确认）
- [ ] 是否有文档的身份（标题/内容/定位段）不匹配？
- [ ] 是否有 orphan 文档（未被任何索引引用）？
```

## 五、扩展机制

### 5.1 本工作流的通用性

本工作流的核心模式——"理解规范 → 全量审计 → 任务规划 → 分阶段执行 → 交叉核验 → 读者评估 → 体系补充 → 最终复查 → 汇报清理"——不限于文档治理。同样的模式可应用于：

- **测试覆盖治理**：理解测试哲学 → 全量测试审计 → 补齐缺失覆盖 → 交叉核验 → 汇报清理
- **代码卫生治理**：理解 AGENTS.md 注释纪律 → 全量代码审计 → 清洁违规 → 交叉核验 → 汇报清理
- **API 一致性治理**：理解接口规范 → 全量 API 审计 → 统一不一致 → 交叉核验 → 汇报清理

### 5.2 创建新域 skill 的模板

为另一个领域创建类似 skill 时，遵循以下步骤：

1. 找到该领域的"规范文档"（相当于 WRITING_GUIDE）
2. 将规范文档中的规则转化为可检查的清单项
3. 按目录/模块拆分审计范围
4. 设计自动化扫描的正则表达式
5. 创建临时任务文档模板
6. 在 `.opencode/skills/<domain>/` 下创建 `SKILL.md`
7. 在 `AGENTS.md` 中添加指针

### 5.3 Skill 文档的存放位置

按照 opencode 的 skill 机制，所有 skill 文档放在 `.opencode/skills/` 下：

```
.opencode/skills/
├── doc-governance/
│   └── SKILL.md                  # 文档治理工作流
├── test-governance/              # 未来：测试治理
│   └── SKILL.md
├── code-hygiene/                 # 未来：代码卫生
│   └── SKILL.md
└── ...
```

每个 skill 是一个独立目录，目录内包含 `SKILL.md`（opencode 自动扫描 `**/SKILL.md` 发现 skill）。SKILL.md 必须包含 YAML frontmatter：`name`（小写连字符，与目录名一致）、`description`（覆盖 what 和 when 两个维度）。

`.opencode/skills/` 独立于 `docs/`（面向人类读者的技术文档）和 `tasks_docs/`（面向项目管理的任务追踪），是面向 AI 智能体的操作知识体系。

### 5.4 与 AGENTS.md 的集成

`AGENTS.md` 是进入本仓库后的第一入口。它**只放指针和硬规则**（单点真理原则）。当新增 skill 后，在 `AGENTS.md` 中添加指针：

```markdown
5. `skills/doc-governance.md` — 执行文档治理前必读
```

注意：AGENTS.md 中使用 `skills/` 路径别名（对应 `.opencode/skills/`），与项目 README 和 `docs/README.md` 中的"文档分工"说明保持一致。
