## 〇、这东西到底是什么（平实语言 + 具体例子）

**一句话**：一个由引擎管理的"**验证过的答案**"登记簿——LLM 给出的答案先过
**确定性验证**，验证通过才登记进去；之后**同一个问题再出现时直接取登记簿里的值，
不再调用模型**；登记错了可以**更正**（必须写理由，原值保留可查）；**全部历史可审计**。

**它解决的具体问题**（试用方 e25 实证的故事）：
试用方做一个"读语篇、解释词义"的确定性自动机。遇到词典外的新词"修炼"，流程是：
LLM 提案词义 → 确定性裁判对照世界模型逐条证据重验 → 证据一致才提交。提交后，
**语篇里每次再出现"修炼"都直接查表（0 次 LLM 调用）**；证据不足的词（如"跑步"）
**不登记**（查表未命中，继续走 LLM）；已提交条目被新证据推翻时**更正**
（原值留在审计轨迹里，可追溯"什么时候、为什么改的"）。
试用方实测：这套机制目前只能写在外部 Python 里。要成为**语言级机制**（"机器持有的
知识是类型化、门控、可审计的"），IBCI 需要提供这个登记簿。

**IBCI 脚本里的形态（示意，API 名待定见 §一）**：

```ibci
import ai

# —— 第一次：问模型 → 确定性验证 → 登记 ——
str answer = @~ 在修真世界观中，"修炼" 指什么？ ~
bool ok = answer.len() > 0 and (answer.contains("修炼") or answer.contains("修行"))
if ok:
    ai.register_answer("term:修炼", answer)   # 引擎校验后登记

# —— 之后再遇到同一个问题：查表命中 → 0 次 LLM 调用 ——
opt stored = ai.lookup_answer("term:修炼")
if stored.is_some():
    str use = stored.unwrap()                 # 直接用登记值（引擎不调模型）
else:
    str use = @~ 在修真世界观中，"修炼" 指什么？ ~  # 未登记才问模型
    # ... 验证通过后 register_answer
```

**它不是什么**（边界，防止过度设计）：
- 不是通用缓存：原始 LLM 输出**不可**直接登记（必须过确定性验证门）——这是铁律
  （判定只来自确定性规则）在机器层的执行；
- 不是向量记忆/语义检索：键是**显式字符串**，不做"相似问题自动命中"（模式匹配
  检索是另一机制，依赖 PT-FEAT-16 的 embedding/检索面，不在 v1 范围）；
- 不是用户层 dict：用户层 dict 缓存做不到 ① 引擎内持久化（随 save_state 跨会话）
  ② 验证门机器强制 ③ 更正/审计轨迹——这三点是"语言级机制"与"应用层惯例"的分界。

## 二、设计问题清单（全部展开；每问：选项 / 推荐 / 依据）

### Q1 登记值：存什么、以什么形态存

- 值类型 = 任意 IBCI 值（`any`，试用方 spec 原样）；
- **存值时深克隆为冻结快照**（选项：① 深克隆[推荐] ② 存引用）：若存引用，用户后续
  修改原对象会污染已登记"验证过的答案"（P10 引用语义陷阱在登记簿上的放大）→
  审计轨迹失真。深克隆复用既有 `deep_clone` 机制（值语义契约），不可克隆值按既有
  回退语义处理（文档化）。
- **推荐：深克隆**。

### Q2 验证门（check）：铁律如何机器强制

- 形态 = `register_answer(name, value, check)` 第三参 `check` = 确定性函数
  （`fn`），**引擎在登记时求值 `check(value)`**：返回假 → **fail-fast 错误**
  （诊断码 + 指明"未通过验证门，拒绝登记"）——不静默返回 false（"拒绝登记"是纪律
  事件，必须显式；与 fail-fast 优于静默回退一致）。
- **"确定性"如何保证**（选项：① 编译期检查[推荐] ② 运行期探测 ③ 不检查）：
  - ① check 函数体内含 LLM 调用（行为表达式 / llm 可调用类 / run_batch / 流式）
    → **编译期 SEM 错误**（新增语义错误 = 语义错误集变更，需全量 pytest 评估——
    这正是 P0-1 诊断面的消费项：该错误须带 ibci 源行定位）；
  - ② 运行期能力探测 = code-odor 红旗（反射/能力探测），拒；
  - ③ 不检查 = 铁律只是惯例，登记簿无法自证"此条经过验证"，拒。
- **推荐：① 编译期检查 + 引擎登记时求值 + 失败 fail-fast**。
- 推论（用户注意）：check 是"谓词即代码"——用户为自己的世界模型写验证逻辑
  （纯 IBCI 确定性代码），这正是试用方"用户按自己的世界模型写谓词，可审计"的原意。

### Q3 查表与"跳过 LLM"：命中发生在哪里（试用方 spec 留了两个形态，这是最大分歧点）

- 试用方原文路由纪律："行为表达式引用已结晶实体时优先走 registry（是否跳过 LLM 由
  用户显式声明，**如 `@~...~` 与 `ai.lookup` 组合，或 llm 可调用类配置
  `"crystallized": "name"`**）——默认不改变现有 `@~...~` 语义"。即：
  - **(a) 用户显式组合**：用户代码里 `lookup` 命中则不调 `@~...~`（if/else 由用户写）；
  - **(b) 引擎层声明路由**：llm 可调用类配置里声明键名，引擎执行该 LLM 调用前先查
    登记簿，命中则**整条 LLM 管线不启动**（用户代码不写 if/else）。
- **关键事实**：(a) 形态**已经省掉调用本身**——if/else 的 else 分支（`@~...~`）
  未命中时根本不执行，LLM 管线不启动。试用方"用户层 dict 缓存做不到引擎内路由"
  的论证不否定 (a)：(a) 已是语言层（ai 模块）且省的是调用本身；(b) 的增量只是
  **省去用户写 if/else 样板**。
- (b) 的成本（v1 不做的理由）：llm 可调用类配置新增 `"crystallized"` 键 = 新契约面；
  交互问题倍增（命中是否进 llmexcept 帧？call_info 是否记录？与 intent snapshot 的
  关系？run_batch 并行项的读写竞态？）——而它带来的只是样板便利。
- **推荐：v1 = (a) 显式组合**（`register_answer` + `lookup_answer` 两函数即可支撑
  全部实用场景）；**(b) 引擎层路由 = 明确挂起的扩展项**——若实际使用证明 if/else
  样板成为真实成本，届时在 (a) 的存储机制上增量设计（零返工）。
- **此点与试用方原始强调（"引擎层路由纪律"）存在分歧，提请用户特别确认。**

### Q4 键（name）

- 显式字符串键（`str`，试用方 spec 原样）。命名约定（如 `term:修炼`、`rule:否定辖域`）
  = 文档惯例，**不做机器强制**（机器强制命名空间 = 无消费者的复杂结构）。
- **重名登记**（选项：① fail-fast 错误[推荐] ② 静默覆盖）：覆盖已验证条目 = 审计
  漏洞（无理由、无轨迹）；"修改"的机器路径是 `correct_answer`（强制理由 + 轨迹）。
  **推荐：① 重名 register = 错误**（"登记"与"更正"机器上强制区分）。

### Q5 更正（correct）

- 形态 = `correct_answer(name, new_value, reason)`：**append-only**——原条目保留在
  审计轨迹，新值成为当前值（指针切换，非覆写）；`reason` = **强制非空字符串**
  （机器校验：空理由 = fail-fast 错误——审计链的"为什么改"不可缺）。
- **新值是否再过 check 门**（选项：① 是[推荐] ② 否）：不过门 = 更正通道变成无门控
  写口（铁律漏洞）；① 复用该条目的 check（登记时已存）——更正值必须同样通过验证。
  **推荐：①**。
- **刚性条目（不可更正）**：试用方 e25 有"刚性词条证伪 = 数据错误（不更正）"的
  领域语义（公理类条目不可改）。**v1 不做刚性标记**（全部可更正；"刚性"是用户领域
  纪律，不需要机器强制——需要时用户约定不调 correct 即可）；`register_answer(...,
  rigid=true)` 留作扩展（correct 对 rigid 条目 = fail-fast）。提请确认 v1 边界。

### Q6 审计（log）

- 形态 = `answer_log(name)` → 事件序列 list：每事件 = {seq, kind(登记/更正),
  值, 理由, check 名}。
- **时间戳问题**（选项：① 引擎事件序号[推荐] ② 墙钟时间 ③ 两者）：墙钟不可复现
  （跨运行审计轨迹不一致，违反确定性纪律）；引擎事件序号（单调递增）= 可复现、
  可排序、无依赖。**推荐：①**（试用方 spec 写"时间"，此处按确定性纪律细化，提请确认）。
- 条目从未存在时 `answer_log` = **空 list**（"从未登记"是合法状态，非错误）。

### Q7 生命周期与作用域

- **引擎级状态**（不是脚本变量，不是 intent snapshot 内容）：
  - 不进 intent snapshot（快照 = 认知作用域/M 纸带；登记簿 = 引擎知识状态/D 纸带
    ——两纸带分离，机制上不应混叠）；
  - **随 `ihost.save_state`/`load_state` 持久化**（选项：① 默认纳入[推荐] ② 显式开关）：
    "用得越久越确定"的跨会话基础就在 save/load——不纳入则每次新进程登记簿清零，
    机制价值减半。纳入 = 与既有平铺池+UID 侧表同构（试用方 spec 原话"不引入新存储
    范式"）。**推荐：① 默认纳入**，请确认。
- **并发**（run_batch 并行项）：v1 = **单写者纪律**——登记/更正只发生在主脚本流
  （append-only 事件流单写者）；并行项**可读**（读 = 快照一致，Python GIL 单操作
  原子）。显式文档化；"并行项写登记簿"不做特殊支持（需要时按并发子系统纪律另设计）。
  提请确认 v1 边界。

### Q8 错误面（fail-fast 清单，归 P0-1 诊断面）

| 操作 | 失败情形 | 处置 |
|------|---------|------|
| register | check(value) 返回假 | 错误（诊断码 + "未通过验证门"） |
| register | name 已存在 | 错误（"已存在，改用 correct_answer 或新键"） |
| register（编译期） | check 函数体含 LLM 调用 | SEM 错误（带 ibci 源行——P0-1 消费项） |
| lookup | name 不存在 | **非错误**：返回 null（未登记 = 合法状态） |
| correct | name 不存在 / reason 空 / check 不过 | 错误 |
| log | name 不存在 | 非错误：空 list |

- 诊断码域：候选 ① `RUN_` 新子码（RUN_ANSWER_*）[推荐：登记簿 = 运行时引擎状态，
  非模型 I/O 面（EMB_ 是 embedding 面、LLM_ 是调用面）] ② 新独立域——独立域为 4
  个码开域过重。**推荐：①**，随 P0-1 诊断面设计一并定码。

### Q9 可观测性（call_info）

- **命中登记簿 ≠ LLM 调用**（是查表）→ call_info（"最近一次 LLM 调用"观测面）**不
  记录命中**；登记簿自身的观测面 = `answer_log`。若 (b) 引擎路由未来落地，其命中
  观测在 (b) 的设计里解决。**v1 按此，请确认。**

### Q10 mock 模式

- mock 模式下 register/lookup 全可用（确定性，测试断言友好——试用方验收实验正是
  mock 断言 + live A/B 双轨）；登记簿内容与 mock 值无交互（登记簿先于调用）。
  v1 无需特殊处理（注记，非问题）。

| 做（v1） | 不做（扩展/挂起） |
|---------|------------------|
| 4 API（register/lookup/correct/log，命名待 §一 确认） | (b) 引擎层声明路由（Q3 推荐挂起） |

## 三、验收基线（试用方原验收改写到 IBCI 形态 + 补充 fail-fast 用例）

1. **试用方原验收**（e25 机制改写为 ibci 脚本，mock 断言 + live A/B 双轨）：
   6 句语篇流，"修炼" 在 U3 后 `lookup_answer("term:修炼")` 命中且后续 0 次 LLM
   调用；"跑步" 保持未登记（lookup 返回 null）；`correct_answer` 后 `answer_log`
   含原值与理由。
2. **补充 fail-fast 判别**（P0-1 诊断面格式）：check 不过 → 登记拒绝错误；重名
   登记 → 错误；check 含 LLM 调用 → 编译期 SEM（带源行）；correct 空理由 → 错误；
   lookup 未登记 → null（非错误）；save_state/load_state 后登记簿保真。
