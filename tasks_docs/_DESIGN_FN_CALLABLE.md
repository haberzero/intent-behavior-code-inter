# 设计分析：`fn` / `callable` 关键字体系彻查与重构方向

> 2026-08-14 编制。触发：裸函数赋 `callable` 槽被拒（类型身份断层的用户可见显现），
> 用户指出 `fn`/`callable` 现设计易致强烈误解、直觉认为 `callable` 存在价值不大，
> 要求从远期收益/架构一致性/语法设计统一/设计语言一致四维彻查。
> 本文件为**设计阶段文档**（任务控制层），不写进 docs/；待语义方向拍板并落地后收敛。

## 〇、彻查结论（先行）

1. **`callable` 作为用户类型是"内部概念泄漏"**：它本是运行期函数对象基类名 + 公理族根
   + fn 推断失败兜底类型，被暴露成可写类型注解；与文档明确声明的"不引入统一 callable
   基类"哲学（`docs/subsystems/03_callable_fn.md` §设计决策）**直接矛盾**。
2. **`callable` 作为用户类型是半成品**：只对 lambda/绑定方法/behavior 生效；裸函数、
   可调用类实例、容器全部失败（实证见 §二）。它唯一比 `fn` 强的地方是"强制可调用"
   （拒绝 42），但该能力也因"拒裸函数"而过严。
3. **`fn` 位置语义不一致**：声明处强制可调用（`fn f = 42` 拒），参数/返回处完全动态
   （`func apply(fn cb); apply(42)` 放行、`-> fn: return 42` 放行）——同一个词在不同
   位置行为割裂。
4. **设计语言"同名不同物"**：`callable` 一词承载四义——运行期函数对象基类名
   （`type(make)`="callable"）/ 公理族根 / 用户类型注解 / `thread(callable=...)`
   关键字参数名。

## 一、实证画像（各位置行为，2026-08-14 实测）

| 位置 | `callable` | `fn` | `fn[(...)]` |
|---|---|---|---|
| 变量 = 裸函数 | ❌ SEM"不能赋" | ✅ 推断具体签名 | ✅ 签名匹配 |
| 变量 = lambda | ✅ | ✅ fn_callable[T] | ✅ |
| 变量 = 绑定方法 | ✅（断层修复后） | ✅ | ✅ |
| 变量 = 可调用类实例 | ❌ SEM"不能赋" | ✅ 推断 Adder | — |
| 参数 = 裸函数 | ❌ SEM | ✅ | ✅ |
| 参数 = 非可调用(42) | ✅ 拒绝 | ❌ 放行（太松） | ✅ 拒绝 |
| 返回 = 裸函数 | ❌ SEM | ✅ | ✅ |

| 重赋值不同签名 | ✅ | ✅ | — |

关键矛盾：
- `callable` 拒"裸函数""可调用类实例"——恰恰是设计文档说 `fn` 要承载的两类
  （03_callable_fn.md 表格）。
- `callable` 唯一净优势 = 参数/返回处"强制可调用"（拒 42）；`fn` 在这些位置太松。
- `fn` 声明推断失败时**内部回退到 `callable` 类型**（`_statement_visitors.py:290-302`
  三处 `resolve("callable")`），`callable` 还是 fn 的兜底类型——两概念在实现层纠缠。

## 二、设计意图考古

- `docs/subsystems/03_callable_fn.md` §设计决策：**"不引入统一 callable 基类"**，
  `fn` 是类似 `auto` 的**类型推断哨兵**而非内置类型；鸭子类型 + 能力协议（`__call__`）
  哲学；所有实现公理层 `__call__` 的类型都可由 `fn` 承载。
- `docs/architecture/03_type_system.md` §7 只定义 `fn`（§7.2 推断）与 `fn[(...)]`
  （§7.3 签名），**没有把 `callable` 作为用户类型设计**。
- 代码却存在 `callable` 用户类型注解（CALLABLE_SPEC，FUNCTION kind），且四重含义。
- **推论**：`callable` 用户类型是运行期基类名/公理根的内部形态被暴露为可写类型，与
  文档哲学直接冲突，且从未被完整接线。

## 三、四维评估

### 架构一致性
- `callable` 类型 = 事实上的"统一可调用基类"，与文档"不引入统一基类 + 鸭子类型"矛盾。
- `callable` 与 `fn`（动态）职责重叠（都想表达"任意可调用"），是**双通道**（同一决策
  两套实现）。
- `callable` 的 FUNCTION kind 是历史遗留（FUNCTION 三义：抽象类型/推断哨兵/真实签名
  共用一个 kind——本次断层修复时已按名特判，暴露此不纯）。

### 语法设计统一性
- 三个形态表达"可调用"：`callable`（抽象类型）/ `fn`（推断+动态）/ `fn[(...)]`（签名）。
- `fn` 一词承载 3+ 种位置语义（声明推断 / 参数返回"任意" / 签名语法），位置不同行为
  不同——用户无法从语法预知 `fn` 在参数处是"含非可调用"、在声明处是"强制可调用"。

### 设计语言一致性（design-philosophy §八：命名粒度统一）
- `callable` 四义同名：运行期类名（type(make)="callable"）/ 公理根 / 用户类型 / thread
  参数名。
- `type(make)` 返回 "callable"（运行期身份），但用户写 `callable` 类型却收不了裸函数
  ——同一词在"类型名"与"运行期身份"上割裂。

### 远期收益
- 现状是语义混乱源，持续误导用户与后续开发者（用户已感到强烈误解）。
- 放任不管，HOF/泛型/可调用体系后续扩展都会继续在三重叠概念上打补丁，架构债累积。

## 四、候选终态

### 方向 A：`callable` 降级为纯内部概念，用户面统一为 `fn` 族（推荐）
- 移除用户可写 `callable` 类型注解（`callable f` / `-> callable` 报清晰错误）。
- `callable` 保留内部角色：运行期函数对象基类名（type(make)="callable" 不变）、
  公理族根、fn 推断兜底。
- 修复 `fn` 位置一致性：参数/返回处 `fn` = "任意可调用（强制）"，拒绝非可调用
  （`apply(42)`、`-> fn: return 42` 编译期拦截）。
- `fn[(...)]` 不变（签名约束）。
- 收益：单一概念族（`fn` = 可调用抽象，声明推断/抽象槽/签名约束三态清晰）；消除与
  文档哲学矛盾；移除半坏关键字；`fn` 参数/返回获得"强制可调用"（补上 `callable` 曾
  独有的能力）。
- 代价：破坏性（现有 `callable` 类型用法 → `fn`）；`fn` 参数/返回语义收紧是行为变更；
  运行期名 "callable" 与用户面 "fn" 不一致（须文档说明 type(make)="callable" 为内部
  基类名）。

### 方向 B：修复 `callable` 为真正的抽象类型（备选）
- 让 `callable` 接受所有可调用（裸函数/可调用类实例/lambda/绑定方法/behavior）。
- 保留 `fn` 动态 + `fn[(...)]` 签名。
- 收益：改动小；`callable` 成为"强制可调用、不钉签名"的抽象宽槽。
- 代价：保留两个"任意可调用"概念（callable 强制 / fn 动态），混淆仍在；与"不引入
  统一基类"哲学矛盾仍在；需为 FUNCTION/CLASS-with-__call__ 补 assignability 特判。

## 五、推荐与待决断项

**推荐方向 A**。依据：与文档声明的鸭子类型哲学一致（fn = 推断哨兵，不引入统一基类）；
单一概念族消除"同名不同物"；移除半坏关键字远期收益最大；`callable` 作为内部基类名/
公理根仍有其位，只是不暴露为用户类型。

## 六、定案与实施（2026-08-14 用户拍板）

- **方向 A 定案**：移除用户面 `callable` 类型注解；`callable` 降级为纯内部概念
  （运行期基类名 `type(make)`="callable" + 公理族根 + `thread(callable=...)` 参数名，
  保持并文档说明）。
- **`fn` 收紧定案**：参数/返回处 `fn`＝"任意可调用（强制）"，拒绝非可调用
  （`apply(42)`、`-> fn: return 42` 编译期拦截）；动态实参/返回（any/auto）放行。
- 实施：守卫三注解解析器（`_resolve_type` / `_resolve_annotation_spec` /
  `_annotation_to_typeref`，IbName + IbSubscript base）对 `callable` 报
  `SEM_UNRESOLVED_TYPE`；`_infer_fn_type` 兜底 `resolve("callable")`→`resolve("fn")`；
  `_check_call_arg_type` + `visit_IbReturn` 加 bare-fn 强制可调用检查。
- 测试迁移 + 判别性回归（`TestCallableInternalization` 4 + `TestFnCallabilityEnforcement`
  10）；文档同步（KNOWN_LIMITS §七 / 03_callable_fn / 03_type_system §7 / 05_functions §5.6）。
- 已知残留（本次范围外）：`list[fn]` 容器元素级强制可调用未接线（动态元素含非可调用）。
